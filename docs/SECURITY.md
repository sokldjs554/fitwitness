# 보안·견고성 점검 (2026-10-29)

공개 데모는 익명 방문자마다 작업 공간을 하나씩 주고, 그 안에서 청구 심사와 지급 기록까지 돕니다. 돈은 합성이지만 "한 번만 지급", "두 사람 승인", "시간당 한도"는 코드가 지켜야 하는 주장이어서, 화면이 아니라 API와 코드 경로에서 깨지는지 점검했습니다.

## 방법

- 별도 AI 에이전트 셋이 서로의 결과를 보지 않고 읽기 전용으로 점검했습니다(보안·견고성, 문서 일관성, 코드·테스트·CI). 서버·DB·유료 API는 쓰지 않았고, 순수 함수와 pydantic 모델을 가져와 재현했습니다.
- 에이전트의 보고는 증거로 쓰지 않았습니다. 이 문서의 "고친 것"은 제가 코드 경로를 직접 읽어 사실임을 확인하고, 고친 뒤 그 경로를 재현하는 테스트를 쓴 것만 담았습니다. 확인하지 못한 것은 맨 아래에 이유와 함께 남겼습니다.
- 사람이 하는 침투 시험이나 외부 감사가 아닙니다. 점검한 범위는 `api`, `runtime`, `storage`, `claims`, `agents`, `retrieval`, `verification`, Dockerfile, `render.yaml`, 워크플로입니다.

## 같은 날 오후에 더한 것과 그 보안 쪽 성질

점검 뒤에 기능을 더하면서 새로 생긴 면을 같은 기준으로 적습니다.

- **라이브 모델 읽기(선택, 기본 꺼짐).** 공개 데모가 돈을 쓸 수 있는 유일한 경로이므로 상한을 코드로 걸었습니다: 건당 예산(호출 전 차단), 하루 상한(DB에서 한 문장으로 예약, 동시 요청이 합쳐서 넘지 못함), 체험 공간당 횟수, 반복된 멱등 키는 예약하지 않음. 꺼져 있으면 키가 있어도 아무것도 하지 않습니다(`FITWITNESS_LIVE_DEMO=on`이 정확히 있어야 함). 켜면 worker 프로세스가 `ANTHROPIC_API_KEY`를 환경에서 읽습니다(세션 비밀과 지표 토큰만 worker 환경에서 뺍니다). 하루 최대 비용은 운영자가 정한 `FITWITNESS_LIVE_DAILY_USD`입니다. 가짜 모델로만 시험했고 실제 호출은 켠 뒤의 첫 실행이 처음입니다. 자세한 설정은 [DEPLOYMENT.md](DEPLOYMENT.md).
- **서명된 승인 기록.** 담당자 답변을 API가 받을 때 서버 키로 HMAC 영수증을 붙입니다. 키는 세션 비밀에서 용도별로 파생하며 API 프로세스만 가집니다(지급을 움직이는 worker는 영수증을 옮겨 적기만 함). 클라이언트가 보낸 영수증은 버립니다. **이것은 DB의 승인 기록이 나중에 고쳐졌는지를 보여 줄 뿐, 공개 데모에서는 답한 사람이 누구인지를 증명하지 않습니다.** 서버 비밀이 새면 영수증을 위조할 수 있고, 비밀을 바꾸면 이전 영수증은 검증되지 않습니다(키 교체 절차는 없음). 2026-10-29 밤에 더한 담당자 신원(`api/identity.py`, [DEPLOYMENT.md](DEPLOYMENT.md#담당자-신원-oidc))을 켜면 답변마다 OpenID Connect ID 토큰이 있어야 하고, 토큰이 증명한 계정(`iss#sub`)이 담당자로 기록되어 영수증에 함께 서명되며, 2차 승인은 이름이 아니라 계정이 달라야 합니다. 토큰은 서명(RS256·ES256)·발급자·대상·만료를 검사하고 권한은 읽지 않습니다. 공개 데모는 이 설정이 없어 익명 그대로입니다.
- **코퍼스 변경 카운터와 트리거.** 검색이 읽은 것을 재사용하기 위해 `fw_corpus_version`과 문장 단위 트리거를 DB에 두었습니다. 트리거 함수는 `SECURITY DEFINER`이고 `search_path`를 고정했으며 트리거 함수라 직접 호출할 수 없습니다. 요청 역할은 자기 테넌트의 행만 읽을 수 있고 쓸 수 없습니다(행 수준 보안, `SELECT` 권한만). 카운터가 틀려 낡은 상태를 재사용하면 검색이 낡은 도면을 돌려줄 수 있으므로, 쓰기가 카운터를 못 올리는 경우를 시험으로 막았습니다: 개정판 추가, 사실 추가, 벡터 쓰기, 사실 삭제, 개정판 수정(SQL 직접), 철회, 롤백된 쓰기, 다른 테넌트의 쓰기. 마지막으로 읽은 카운터와 읽는 도중의 변화는 읽기를 다시 합니다.
- `fw_live_spend`와 `fw_admission`은 행 수준 보안 없이 소유자 역할로만 읽고 씁니다(전역 한도라서 테넌트 열이 없음). 요청 역할에는 권한이 없습니다.

## 확인했고 문제가 없던 것

- **테넌트 격리.** 모든 데이터 경로가 `scope` 의존성과 트랜잭션 로컬 `SET ROLE`(행 수준 보안, FORCE) 아래에서 돕니다. 기본 키가 `(tenant_id, id)`라 결정적 ID가 테넌트 사이에 겹쳐도 섞이지 않습니다.
- **세션 쿠키·CSRF.** 서명 + 소금 + 만료 1시간, `HttpOnly`, `SameSite=Lax`, Render에서는 `Secure`. 비안전 메서드는 Origin을 허용 목록과 정확히 비교하고 `Origin: null`을 거절합니다.
- **경로 이동·업로드.** 파일을 서빙하는 경로는 정규식으로 이름을 고정하고, 사용자가 올리는 파일이 없어 PDF·이미지 파서에는 서버가 심은 합성 파일만 들어갑니다.
- **셸 검색 도구.** 셸이 아니라 허용 목록 파서입니다(프로그램 열 개, 플래그 허용표, 리다이렉션·글롭·`..`·절대 경로 거절, rlimit, 5초 제한). 기본은 꺼져 있습니다.
- **SQL.** 값은 모두 바인딩합니다. **비밀 정보.** 추적 파일과 `git log -S`에서 API 키·토큰·개인키 패턴이 나오지 않았습니다. **XSS.** `dangerouslySetInnerHTML`·`innerHTML`·`eval`이 없습니다.

## 고치지 않은 것과 이유

- **공개 데모에는 계정·SSO가 없습니다.** 담당자 이름은 입력한 문자열이고, "서로 다른 두 사람"은 이름이 다르다는 뜻입니다. 운영자가 OIDC를 설정하면 계정으로 바뀌지만([DEPLOYMENT.md](DEPLOYMENT.md#담당자-신원-oidc)) 실제 IdP에 붙여 본 적은 없고, 시험은 테스트가 만든 가짜 발급자와 GitHub Actions가 실제로 발급하는 토큰(workflow `oidc-real-issuer`, 26개 점검)으로 했습니다. 공개 데모는 설정하지 않아 익명이며 화면에도 적혀 있습니다.
- **`X-Forwarded-For` 위조로 주소별 한도를 피할 수 있었던 것(2026-10-31 확인, 고침).** 공개 데모에서 실제로 재현됐습니다(시간당 주소당 20개 제한을 직접 쓴 헤더로 피함, [DEPLOYMENT.md](DEPLOYMENT.md)). `api/visitor.py`가 믿는 프록시가 덧붙인 항목만 세도록 고쳤고 단위·통합 테스트가 지킵니다. 첫 고침(믿는 프록시 하나)은 배포 뒤 probe에서 틀린 것이 드러났습니다. 맨 오른쪽 항목이 요청마다 바뀌는 앞단 주소라 주소별 한도가 아예 세지 않았고([실행 41224993810](https://github.com/sokldjs554/fitwitness/actions/runs/41224993810)), 기본값을 2로 고친 판도 일부 요청을 놓쳤습니다(앞단 항목의 수가 요청마다 달라서, [실행 41226556755](https://github.com/sokldjs554/fitwitness/actions/runs/41226556755)). 지금은 Render에서 Cloudflare가 쓰는 `CF-Connecting-IP`를 세고 `X-Forwarded-For`는 그 헤더가 없을 때만 읽습니다. `d4094dc` 배포 뒤 같은 probe로 확인했습니다([실행 41230129960](https://github.com/sokldjs554/fitwitness/actions/runs/41230129960)): 21번째에서 막히고 꾸민 헤더 넷이 모두 막혔습니다(셋은 앱이 429, 꾸민 `CF-Connecting-IP`는 Cloudflare가 403). Cloudflare를 거치지 않는 요청이 원점에 닿을 수 있는지는 재지 않았습니다. 어느 경우에도 전체 시간당 100개 한도는 그대로였습니다.
- **Neon 소유자 계정은 `BYPASSRLS`입니다.** 요청 경로는 `SET ROLE`로 RLS를 받는 역할이 되지만, `connection()`을 거치지 않는 코드(`plain()`)가 새로 생기면 곧바로 RLS를 우회합니다. 지금은 입장 한도·세션·디스패치 큐에만 쓰입니다.
- **지급 직후의 비재시도 오류.** 원장에 쓴 뒤 이벤트 기록에서 일시적 DB 오류가 나면 그 실행은 `failed`가 됩니다. 원장 행은 이미 있고 같은 청구의 재실행은 `already_paid`를 돌려주므로 이중 지급은 아니지만, 담당자가 그 실행을 실패로 보게 됩니다.
- **셸 검색의 `preexec_fn`.** 하트비트 스레드가 있는 프로세스에서 쓰면 문서상 교착 위험이 있습니다. 기본이 꺼져 있고 공개 데모에서는 모델이 없어 닿지 않습니다.
- **디스크 용량.** 세션 하나가 약 3.5 MB라 시간당 100개면 350 MB로 Neon 무료 한도(0.5 GB)에 가깝습니다. 세션 청소는 세션 생성 때 호출당 20개씩만 돕니다.
- **공급망.** GitHub Actions는 태그로, 베이스 이미지는 다이제스트 없이 고정했습니다. `dependabot.yml`로 갱신을 받게 했지만 SHA 고정은 하지 않았습니다. `pip-audit`·`npm audit`은 네트워크가 없는 환경이라 돌리지 못했습니다.
