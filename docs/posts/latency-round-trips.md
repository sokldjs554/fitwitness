# FitWitness 공개 서버의 대기 시간: 데이터베이스 왕복과 worker 기동

공개 서버에서 체험 공간 하나를 만드는 데 14초에서 19초가 걸렸습니다. 도면 20개와 청구 8건을 데이터베이스에 넣는 작업이고, 로컬에서는 같은 시드가 1.3초였습니다. 무료 CPU가 느린 탓만은 아니라는 뜻이었습니다.

이 프로젝트의 코드는 대부분 Claude Code가 썼습니다. 저는 무엇을 잴지 정하고, 숫자를 재고, 나온 값을 확인하는 일을 맡았습니다. 아래 숫자는 모두 저장소의 커밋 메시지와 docs 문서에 적힌 값입니다. 공개 서버에서 잰 값도 docs/WORKFLOW.md에 옮겨 적어 두었습니다.

원인은 데이터베이스까지의 왕복이었습니다. 웹 서버는 Render, 데이터베이스는 Neon이고 둘 다 싱가포르에 있지만 서로 다른 서버라서, 질의 하나의 왕복을 10ms 안팎으로 잡았습니다. 거리보다 횟수가 문제였습니다. 요청 단위 작업마다 새 TLS 연결을 열었고 질의 앞에 설정문 두 개를 보냈습니다. 연결 비용이 질의 비용보다 컸고, 실행 한 건이 그런 작업을 수십 번 했습니다. 커밋 메시지에는 공개 서버에서 파이프라인 단계 하나에 약 1초가 들었다고 적혀 있습니다.

왕복은 두 가지 방법으로 셌습니다. 하나는 저장소의 연결 블록과 psycopg의 문장 실행, 서버 응답 대기를 감싸는 스크립트입니다. 연결 블록과 문장은 호출한 함수별로, 응답 대기는 전체 횟수로 셉니다. 다른 하나는 로컬 PostgreSQL 앞에 세운 TCP 프록시로, 서버가 보낸 덩어리 수를 왕복의 근사치로 셉니다. 같은 방식의 프록시에 방향마다 6ms씩 기다리게 하면 왕복 12ms의 원격 데이터베이스를 흉내 낼 수 있어서, 응답 시간은 그 뒤에서 쟀습니다.

바꾼 것은 세 가지입니다. 첫째는 연결 풀입니다. 빌릴 때마다 연결이 살아 있는지 확인하는 것도 왕복이라서 30초 넘게 쉰 연결만 확인합니다. 둘째는 연결 블록 하나를 libpq 파이프라인에 태워 BEGIN, 역할 설정, 문장들, COMMIT을 한꺼번에 보내는 것입니다.

```python
with c.pipeline():
    c.execute("BEGIN")
    yield c
    c.execute("COMMIT")
```

문서에는 이렇게 하면 쓰기만 하는 블록은 왕복 한 번, 결과를 읽는 블록은 두 번이라고 적었습니다. 셋째는 이미 읽은 데이터를 다시 읽지 않는 것입니다. 실행을 시작할 때 스냅샷, 개정, 사실을 한 번에 읽어 두고, query_dimensions 도구는 그 사실을 넘겨받아 답합니다. 이벤트 기록은 리스 확인, 순번 계산, 삽입을 한 문장으로 합쳤고, 시드는 도면과 청구를 각각 한 트랜잭션으로 넣습니다.

아래는 12ms 왕복을 흉내 낸 프록시 뒤에서 rules provider로 잰 값입니다.

| 측정 | 이전 | 이후 |
|---|---|---|
| 체험 공간 생성 | 4.58초 | 0.63초 |
| 문서 목록 | 1.62초 | 0.07초 |
| 실행 한 건, 프로세스 안 | 3.94초 | 1.38초 |
| 실행 한 건의 서버 응답 대기 | 138회 | 97회 |

실행에는 시간이 하나 더 있었습니다. worker를 시작하는 시간입니다. 예전에는 실행마다 새 Python 프로세스를 띄웠고, 인터프리터 기동과 import에 로컬에서 약 1초, 무료 서버에서는 10초 넘게 걸렸습니다. 미리 띄워 둔 worker로 바꾸자 로컬에서 큐 등록부터 완료까지의 중앙값(4회)이 2.07초에서 0.51초가 됐고, worker 시작까지는 1.65초에서 0.16초가 됐습니다.

첫 버전은 실행이 끝날 때마다 교체 worker를 새로 띄웠습니다. 공개 서버에서 바로 이어 누른 두 번째 실행은 교체 worker가 아직 import 중이라 시작까지 17~21초를 기다렸습니다. 그래서 worker가 끝나지 않고 다음 실행을 기다리게 다시 바꿨습니다. 미리 띄우는 worker는 기본 1개이고 약 90MB를 차지합니다. 동시 실행 둘이 모두 즉시 시작하려면 2로 올려야 한다고 문서에 적었지만, 동시 실행을 잰 값은 없습니다.

위의 이후 값은 로컬과 지연 프록시에서 잰 것이어서, 같은 날 공개 서버에서도 배포 전과 후를 쟀습니다. 이 샌드박스에서 프록시를 거쳐 부르는 값이라 네트워크 한 번 왕복 약 0.3초가 모두 들어 있습니다.

| 공개 서버(무료 인스턴스) | 배포 전 | 배포 후 |
|---|---|---|
| 체험 공간 생성 | 14.4초 | 1.1초 |
| 문서 목록 | 1.9초 | 0.33초 |
| 큐 등록부터 완료, 연속 4회 | 13.6초(두 번째는 21초) | 0.34~0.54초 |
| 큐 등록부터 시작, 연속 4회 | 1.1초(두 번째는 19~21초) | 0.03~0.06초 |

두 커밋이 모두 반영된 뒤의 값입니다. 중간에 첫 커밋만 배포했을 때는 첫 실행이 2.1~2.4초로 줄었지만 연달아 누른 두 번째는 여전히 17~21초였고, 이어서 worker 재사용을 넣은 것입니다. 측정 스크립트와 원본 출력은 저장소에 넣지 않았고, 당시 기록한 값을 WORKFLOW.md에 옮겨 적었습니다.

이 숫자가 보여 주지 않는 것도 있습니다. 로컬 값은 고정 지연을 넣는 프록시 뒤에서 잰 것이라 실제 네트워크의 흔들림이 없고, 10ms도 호스팅 환경에서 따로 잰 값이 아니라 제가 잡은 값입니다. 138과 97은 서버 응답을 기다린 횟수여서 큰 결과가 여러 조각으로 오면 그만큼 늘어나므로 실제 왕복은 더 적습니다. 사용한 측정 스크립트는 저장소에 없어서 같은 방법으로 다시 잴 수 없습니다.

남은 것은 중단 체험의 복구 시간입니다. 새 worker를 띄우는 시간이라 같은 날 9.1초와 13.5초가 나왔고, 대기 worker를 둘로 올리면 줄어들 것으로 보지만 재 보지 않았습니다.
