# 실제 모델이 고르는 경로를 네 번 잰 기록: 실패 2건에서 18/18까지

판정은 맞았는데 길이 틀린 실행이 있습니다. 매 커밋 도는 평가 게이트가 그런 길을 잡아내지만, 그 게이트는 규칙 엔진과 대본으로 고정한 planner의 길만 봅니다. 실제 모델이 어떤 도구를 언제 부르고 언제 멈추는지는 재 본 적이 없었습니다. 2026년 10월 22일에 그것을 네 번 쟀고, 합계 0.40달러가 들었습니다.

이 프로젝트의 코드는 대부분 Claude Code가 썼습니다. 저는 무엇을 잴지 정하고, 숫자를 재고, 나온 값을 확인하는 일을 맡았습니다. 아래 숫자는 저장소의 docs/evaluation/agent-trajectory.json과 docs/evaluation/README.md에 적힌 값입니다.

측정은 이렇습니다. 합성 도면의 test family 6개마다 기준 도면에서 만든 질의 하나를 두고, 먼저 규칙 provider로 돌려 기준 경로를 얻습니다. 그다음 Claude Haiku 4.5로 세 구조를 한 번씩 돌립니다. 계획을 한 번만 세우는 구조, 반복해서 세우는 구조, planner와 반대 역할의 challenger가 따로 있는 구조입니다. 실행마다 0.04달러를 미리 예약하고 끝나면 실제 비용으로 정산하며, 전체 상한을 넘기면 남은 실행은 건너뜁니다. 판정은 결정적 검증기가 내리므로 정확도는 모델의 판단력이 아니라 모델이 고른 경로가 충분했는지를 잽니다. 틀린 판정은 조회하지 않은 도면, 조회했지만 필요한 필드를 다 묻지 않은 도면, 실행이 끝나지 않은 경우로 나눕니다.

1차에서 단일 계획과 반복 계획은 30/30이었고 planner+challenger는 6건 중 2건이 판정 전에 끝났습니다. 오류는 "model output failed schema validation" 한 줄이었습니다. 원문은 artifact에 있었는데 로그를 읽는 곳에서 artifact를 내려받을 수 없어서, Summary 단계가 parse 오류와 raw 출력을 찍도록 바꾼 뒤 그 구조만 다시 돌렸습니다. 이것이 2차이고 0.05달러였습니다.

2차에서 두 가지가 보였습니다. planner가 저장 검색 도구를 정의하면서 채널 이름을 keyword라고 썼습니다. 도구 이름은 search_keyword인데 스키마의 채널 이름은 bm25였습니다. 필드에는 kind를 넣었는데 부품 종류는 치수 필드가 아닙니다. 출력이 스키마 검증에 실패하면 실행은 그 자리에서 끝났습니다. 다른 하나는 challenger가 정의된 적 없는 저장 검색을 호출한 것입니다. "unknown saved tool"로 실행 전체가 실패했고, planner가 이미 도면 다섯 장을 모두 조회해 둔 판정까지 잃었습니다.

고친 것은 셋입니다. 스키마에 맞지 않는 출력은 검증 오류와 보낸 계획을 붙여 한 번만 다시 요청하고, 실패한 턴은 trace에 남기며 비용도 셉니다. keyword는 bm25의 별칭으로 받습니다. 모델이 고른 도구가 여기서 돌 수 없으면 실행을 실패시키지 않고 tool_error 이벤트와 관측으로 남겨 다음 계획에 보여 줍니다.

3차에서 planner+challenger는 30/30이 됐습니다. 대신 다른 두 구조에서 새 실패가 나왔습니다. 단일 계획 구조의 두 family에서 planner가 유일한 계획을 semantic 채널의 저장 검색 정의에 썼습니다. 그 작업 공간에는 임베딩이 연결되어 있지 않아 정의는 돌지 못했고, 한 family에서는 도면 4장이 조회되지 않았으며 다른 하나에서는 두 도면의 필드를 다 묻지 않았습니다. 반복 계획 구조의 두 family는 세 번의 계획 동안 같은 조회를 반복하거나 필요한 필드 하나를 묻지 않은 채 멈췄습니다. 1차에서 같은 코드로 6/6이었던 구조들입니다. 한 번의 실행으로 구조의 우위를 말할 수 없다는 뜻이기도 합니다.

다시 고친 것은 모델에게 주는 컨텍스트입니다. 남은 계획 횟수를 넣었고 단일 계획 구조에서는 0입니다. 후보마다 아직 묻지 않은 필수 필드를 넣었습니다. 저장 검색 정의의 스키마에는 작업 공간에서 돌릴 수 있는 채널만 보이게 했습니다. 4차에서 18건 모두 완료였고 90/90이었습니다.

이 숫자가 보여 주지 않는 것을 적습니다. family 6개, family마다 질의 하나, 구조마다 한 번입니다. 구조마다 6회뿐이라 18/18의 95% 구간은 61%부터 시작합니다. 수정 뒤 같은 family를 다시 돌린 것은 오류 수정의 검증이지 독립 평가가 아닙니다. 검색은 도번과 BM25 채널만 썼고 family 하나의 도면 다섯 장만 색인된 작업 공간입니다. 그리고 4차의 90/90은 더 좋아질 여지가 없는 포화된 결과라서, 회귀를 잡는 데는 쓸 수 있어도 개선의 신호는 주지 못합니다.

남은 것은 1차와 3차에서 드러난 실패 유형을 더 어려운 과제군으로 따로 모으는 일입니다. 거기서는 18/18이 나오면 안 됩니다.
