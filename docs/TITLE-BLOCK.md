# 이미지 도면의 표제란 읽기

`ingest/pdf.py`는 텍스트 층이 있는 벡터 도면의 주석만 읽습니다. 스캔이나 사진으로 만든 PDF처럼 페이지가 그림 한 장이면 읽어 낸 것이 없었고, 실제 기계 도면 12장으로 돌려 보니 정말 0건이었습니다. `ingest/title_block.py`는 그 빈칸을 채우는 첫 단계입니다. 도면의 신원이 적힌 오른쪽 아래 표제란을 OCR로 읽습니다.

## 어떻게 읽나

1. 페이지를 긴 변 6,000픽셀 이하로 그립니다.
2. 오른쪽 아래를 높이가 다른 크롭 3개로 자르고, 각각을 원래 크기, 0.7배, 0.5배로 Tesseract에 넣습니다(희소 텍스트 모드, 원래 크기에서는 블록 모드도). 같은 라벨이 어떤 배율에서는 읽히고 어떤 배율에서는 사라지기 때문입니다. 겹친 자리에서는 신뢰도가 높은 쪽을 남깁니다.
3. 셀 테두리를 글자로 읽은 조각을 버리고, 따로 읽힌 라벨 글자("材", "料")를 합칩니다.
4. 알려진 라벨(`材料`, `比例`, `图号`, `재질`, `MATERIAL`, `SCALE`, `DWG NO` 등)의 바로 오른쪽 칸을 값으로 봅니다. 값이 안 읽혔으면 그 칸만 잘라 키워서 한 줄로 다시 읽습니다.
5. 중국 표준(GB) 표제란은 도번에 라벨이 없습니다. 모양으로 찾습니다. 하이픈이 든 코드("DJZ-02", "QF02-10")나 영문 3자 이상과 숫자("ZPT19")이고, 부품표 머리글(`序号`, `代号`) 아래에 있어야 합니다. 영문 두 글자와 숫자("HT200", "ZL107")는 재질 규격이라 도번이 아닙니다. 쪽 번호("Page-271")와 규격("GB", "ISO")도 아닙니다. 점이 든 코드(`LJT04.20`)도 도번 모양으로 보되, 가는 이탤릭 글꼴이라 O/0, J/I를 혼동하므로 0.70 이상으로 읽었을 때만 받고 숫자 사이의 O는 0으로 되돌립니다. 같은 칸이 점이 있는 코드와 없는 코드로 서로 다르게 읽혔으면 어느 쪽도 쓰지 않습니다. `Ra1.6`, `SR12.5`는 도번이 아닙니다.
5a. 중국 표준 표제란은 재질도 라벨 없이 큰 칸에 적습니다. 구석에서 표제란 자체의 낱말(설계, 制图, 审核, 比例, 阶段标记 등) 셋 이상이 읽히고, 쪽 어디에도 `材料` 라벨과 부품표 머리글이 없으며, 읽힌 재질 규격(`HT150`, `ZL107`, `40Cr`, `60Si2MnA`, 주물·합금강)이 하나뿐일 때 그것을 재질로 봅니다. `45`처럼 숫자만 있는 것은 받지 않습니다. 부품표가 있는 조립도에는 쓰지 않습니다. 이 규칙의 첫 판은 조립도의 부품표에서 `HT200`을 읽어 재질 칸이 없는 도면에 값을 만들었고, 개발용 도면에서 그것을 보고 `材料` 라벨 조건을 더했습니다.
6. 신뢰도 0.6 미만은 보고하지 않습니다. 한 필드에서 서로 다른 값이 비슷한 신뢰도로 읽히면 어느 쪽도 쓰지 않습니다.

읽은 값은 사실이 아니라 **관찰**입니다. `Fact`로 저장되지만 `certainty="uncertain"`, `method="title_block_ocr"`입니다. 검증기는 이런 값으로 일치를 선언하지 않고 "근거 부족"으로 답하며, 근거 목록에는 값을 읽은 페이지 위치(상자)가 실립니다. 오독된 재질이 일치로 바뀌는 일이 없게 한 것입니다.

## 실제 도면으로 잰 결과

공개 벤치마크 [MechVQA](https://github.com/xiaofengShi/MechVQA)의 실제 기계 도면 12장(중국 교재의 도면 페이지, 이미지 파일)입니다. 정답은 도면의 표제란을 눈으로 보고 첫 실행 전에 적었습니다. 도면이 제3자 저작물이라 저장소에는 넣지 않았고, `scripts/eval-title-block.py`가 같은 12장을 받아 다시 재현합니다. 결과는 [`docs/evaluation/title-block-real.json`](evaluation/title-block-real.json)에 있습니다.

| 필드 | 읽음 / 정답이 있는 도면 | 비고 |
|---|---|---|
| 도번 | 10 / 12 | 못 읽은 2장은 이탤릭체 도번(ZPT04, ZPT18) |
| 재질 | 4 / 8 | 못 읽은 4장은 작은 칸의 값(40Cr, LY12, HT200)과 한자 재질(橡胶) |
| 비례 | 1 / 9 | 라벨도 값도 작아 대부분 읽지 못함 |
| 틀린 값을 보고함 | 0 | 보고한 15건이 모두 정답입니다 |
| 칸이 없는데 읽음 | 0 | 조립도처럼 재질 칸이 빈 4장에서 아무것도 만들어 내지 않았습니다 |

도면 한 장에 중앙값 약 11초가 걸립니다(Tesseract가 있는 컴퓨터에서 이미지만 든 PDF일 때만 실행됩니다).

## 새 도면 27장으로 다시 잰 결과 (2026-10-24)

**이 절의 숫자는 읽기 코드를 고치기 전의 것이고, 고친 뒤에는 이 27장이 개발용 도면입니다.** 위 12장은 규칙을 고치며 본 도면이라 홀드아웃이 아닙니다. 그래서 같은 MechVQA 벤치마크에서 12장에 쓴 적이 없는 도면 40장(목록은 정답 파일 `docs/evaluation/title-block-holdout-gold.json`의 키이고 12장과 겹치지 않음을 확인했습니다)을 읽기 코드를 바꾸지 않은 채 다시 쟀습니다. 40장은 시드 20261024로 무작위로 뽑았다고 전달받았지만 뽑는 코드는 저장소에 없습니다. 채점은 `scripts/eval-title-block-holdout.py`이고, 입력으로 쓴 이미지의 SHA-256은 `docs/evaluation/title-block-holdout-images.sha256`에 있습니다. **정답은 Claude 하위 에이전트가 도면 크롭을 보고 적었고, 점수에 든 27장은 2026-10-25에 사람(저장소 주인)이 크롭을 보며 하나씩 확인해 27장 모두 맞았습니다**(확인표 `docs/evaluation/title-block-holdout-label-check.csv`, 고친 라벨 0). 점수에서 뺀 13장(표제란 없음 11, 불분명 2)은 확인하지 않았습니다. 도면이 제3자 저작물이라 확인에 쓴 크롭 이미지는 저장소에 넣지 않았습니다. 2026-10-24에 이 환경(Tesseract 5.3.4, `chi_sim+kor+eng`)에서 원래 12장을 다시 돌려 도번 10, 재질 4, 비례 1이 그대로 나오는 것을 확인했고, 홀드아웃도 이 환경에서 직접 돌린 값입니다.

40장 중 13장은 점수에서 뺐습니다. 볼트·너트 사양표와 제품 웹 페이지처럼 도면 표제란이 없는 11장, 한 페이지에 도면이 둘 이상이라 어느 표제란이 정답인지 불분명한 2장입니다.

| 필드 | 읽음 / 정답이 있는 도면 | 비고 |
|---|---|---|
| 도번 | 4 / 14 | LJT 계열 표제란 9장에서 0 |
| 재질 | 3 / 16 | LJT 계열 9장에서 0 |
| 비례 | 0 / 17 | 사실로 저장하지 않는 필드 |
| 틀린 값을 보고함 | 1 | `LJT02.04`를 `LJT0204`로 읽음(점이 빠짐) |
| 칸이 없는데 읽음 | 0 | 도번·재질 칸이 빈 11장에서 아무것도 만들어 내지 않았습니다 |

도면 한 장에 중앙값 6.8초가 걸렸습니다(원래 12장은 같은 환경에서 12.0초).

다시 돌리려면(도면은 제3자 저작물이라 저장소에 없습니다):

```bash
# 40장을 내려받고(경로는 SHA-256 목록의 두 번째 열) 해시를 확인한 뒤
mkdir -p mechvqa && cd mechvqa
awk '{print $2}' ../docs/evaluation/title-block-holdout-images.sha256 | while read p; do
  mkdir -p "$(dirname "$p")"; curl -sSf -o "$p" "https://raw.githubusercontent.com/xiaofengShi/MechVQA/main/benchmark_data/$p"; done
sha256sum -c ../docs/evaluation/title-block-holdout-images.sha256 && cd ..
uv run python scripts/eval-title-block-holdout.py --images mechvqa/images --gold docs/evaluation/title-block-holdout-gold.json --output /tmp/holdout.json
```

읽는 법입니다. 점수에 든 27장 중 9장이 같은 양식(도번이 `LJT04.20`처럼 점이 든 코드, 재질이 큰 칸 한가운데)이고 이 양식에서는 도번과 재질을 하나도 읽지 못했습니다. 나머지 양식에서는 도번 4/5, 재질 3/7입니다. 앞의 12장 수치(도번 10/12)는 이 읽기 코드가 이미 본 도면의 값이라 일반화 성능으로 읽으면 안 됩니다. 읽기 코드는 이 결과를 보고 고치지 않았고, 고친다면 이 27장이 아니라 아직 쓰지 않은 도면으로 다시 재야 합니다. 라벨은 확인됐지만 27장이라 구간이 넓습니다(도번 4/14는 95% 구간 12~55%, 재질 3/16은 7~43%).


## 읽기 코드를 고친 뒤, 새 도면으로 한 번 더 (2026-10-24)

첫 홀드아웃에서 가장 크게 틀린 것은 한 양식(합비공대 교재, 도번이 `LJT04.20`처럼 점이 든 코드, 재질이 라벨 없는 큰 칸)이었습니다. 읽기 코드에 세 가지를 더했습니다. 점이 든 코드를 도번 모양으로 받고, 점이 있는 읽기와 없는 읽기가 맞서면 어느 쪽도 쓰지 않으며, 표제란 구석의 라벨 없는 재질 규격을 재질로 봅니다(위 5, 5a). 고친 코드는 `e6b0a98`입니다.

**고친 쪽의 점수는 개발용 도면의 것입니다.** 원래 12장은 그대로(도번 10/12, 재질 4/8, 비례 1/9, 틀린 값 0, 칸이 없는데 읽음 0)이고, 첫 홀드아웃이던 27장은 도번 4/14 → 7/14, 재질 3/16 → 8/16, 틀린 값 1 → 0입니다. 규칙을 이 도면들을 보며 썼으므로 일반화 수치로 읽으면 안 됩니다.

**그래서 아직 쓰지 않은 도면 60장을 새로 뽑았습니다**(시드 20261025, 12장과 첫 홀드아웃을 뺀 PNG 314장에서. 뽑는 코드 `scripts/sample-title-block-holdout.py`와 목록 `title-block-holdout2-sample.txt`를 라벨보다 먼저, 읽기 코드를 고친 것보다도 먼저 커밋했습니다). 라벨은 Claude 하위 에이전트 셋이 나눠 도면 크롭을 보고 적었고(`title-block-holdout2-gold.json`) 읽기 코드를 돌리기 전에 커밋했습니다. 60장 가운데 표제란이 있는 도면은 39장, 없는 것은 21장(사양표, 웹 페이지 등)이고, 그 가운데 4장이 불분명했습니다. 점수에는 34장이 들어갑니다. 한 장(`e626c8a6`)은 첫 홀드아웃의 `615c96ae`와 같은 도면이라 개발에 쓴 도면의 복제로 빼고 셌습니다.

**라벨은 하위 에이전트가 적었고, 점수에 든 34장은 2026-10-25에 사람(저장소 주인)이 크롭을 보며 하나씩 확인해 34장 모두 맞았습니다**(확인표 `docs/evaluation/title-block-holdout2-label-check.csv`, 고친 라벨 0). 그 전에 Claude가 세 장(`e626c8a6`, `20b8e44e`, `b6f1dcad`)을 따로 보았습니다. 점수에서 뺀 26장(표제란 없음 21, 불분명 4, 복제 1)은 확인하지 않았습니다.

같은 34장을 고치기 전 코드(`3c45a32`)와 고친 코드(`e6b0a98`)로 한 번씩만 돌렸습니다. 결과를 본 뒤 코드를 더 고치지 않았습니다.

| 필드 | 고치기 전 | 고친 뒤 (95% 구간) |
|---|---|---|
| 도번 | 4 / 16 | **8 / 16** (28~72%) |
| 재질 | 3 / 17 | **8 / 17** (26~69%) |
| 비례 | 0 / 21 | 0 / 21 (사실로 저장하지 않는 필드) |
| 틀린 값을 보고함 | 1 | **4** |
| 칸이 없는데 읽음 | 1 | 1 |

맞게 읽은 것은 도번과 재질 모두 약 두 배가 됐지만, **틀린 값도 1개에서 4개로 늘었습니다.** 새로 틀린 셋은 이탤릭 글꼴의 글자 혼동입니다. `LJT06.17`을 `JT06.17`로(첫 글자 빠짐, 0.76), `LJT04.34`를 `LIT04.34`로(0.84), `LJT03.12`를 `LIT03.12`로(0.82) 읽었고, 전에도 있던 `LJT01.05`를 `LJTO105`로 읽은 것(0.71)이 남아 있고, 도번 칸이 비어 있는 `a1ff0589`에서는 `R2-3`을 도번으로 읽었습니다(0.74, 고치기 전에도 읽음, 무엇을 읽은 것인지는 확인하지 않았습니다). 점이 든 코드의 문턱 0.70은 J/I 혼동을 거르지 못했습니다. 이 틀린 값들은 조건 일치로 쓰이지 않고(읽은 값은 "확인 필요"로만 저장되고 근거에 읽은 위치가 붙습니다), 검증기는 "근거 부족"으로만 답합니다.

읽는 법입니다. 이 34장에서 도번이 있는 16장 중 12장이 같은 합비공대 양식입니다. 개선의 대부분이 그 양식에서 나왔고 다른 양식(`WLJSQ475-008`, `CLYB-00`, `ZD10-001`)은 고치기 전과 같습니다. 이 벤치마크가 한 교재의 쪽들이 대부분이라, 이 점수는 "한 교재의 표제란에 맞춘 코드가 같은 교재의 새 쪽을 더 읽는다"는 것이지 표제란 일반을 읽는다는 것이 아닙니다. 또 이 34장도 결과를 본 지금은 개발용 도면이 되었고, 다음 개선은 세 번째로 뽑는 도면으로 재야 합니다. 다음에 고칠 것은 J/I와 O/0 혼동으로 틀리는 값을 거르는 방법과 `R2-3` 같은 짧은 코드를 도번으로 읽는 것을 막는 규칙입니다. 재현: `docs/evaluation/title-block-holdout2.json`(고친 뒤)과 `title-block-holdout2-before-the-change.json`(고치기 전)은 `scripts/eval-title-block-holdout.py --images <60장> --gold docs/evaluation/title-block-holdout2-gold.json`의 출력이고, 60장은 목록 파일의 경로로 내려받습니다.

## 같은 61장을 Claude가 읽으면 (2026-10-25)

사람이 라벨을 확인한 두 홀드아웃(첫 27장, 새 34장)을 같은 채점으로 Claude Haiku 4.5에게 읽혔습니다(`scripts/eval-title-block-vlm.py`, 수동 워크플로 `title-block-vlm-evaluation`). 한 쪽에 두 번 묻습니다. **쪽**은 쪽 전체를 긴 변 1600픽셀로 줄여 보내고 표제란의 상자와 도번·재질·비례 칸을 읽게 한 것이고, **자름**은 그 상자를 원본 해상도에서 여백 3%를 두고 잘라 다시 읽게 한 것입니다. 두 질문은 첫 호출 전에 스크립트에 고정했고 결과를 본 뒤 바꾸지 않았습니다. 도면은 제3자 저작물이라 워크플로가 MechVQA에서 받아 커밋된 SHA-256과 대조하고, 그림 없이 보고서만 남깁니다.

| 필드 (61장) | Tesseract | Claude, 쪽 (95% 구간) | Claude, 자름 |
|---|---|---|---|
| 도번 | 12 / 30 | **22 / 30** (56~86%) | 20 / 30 |
| 재질 | 11 / 33 | **23 / 33** (53~83%) | 18 / 33 |
| 비례 | 0 / 38 | 32 / 38 | **34 / 38** |
| 틀린 값을 보고함 | 5 | 9 | 6 |
| 칸이 없는데 읽음 | 1 | 7 | 2 |

Tesseract 열은 커밋된 기록을 더한 것입니다. 첫 27장은 고치기 전 코드(고친 코드에는 개발용 도면이라), 새 34장은 고친 코드의 값입니다. Claude는 첫 실행에서 61장 118번 호출에 $0.374(호출당 중앙값 1.6초)였고, 다시 읽은 것을 더해 모두 $0.478입니다. Tesseract는 무료이고 한 장에 중앙값 7~9초입니다.

**어떻게 틀렸나.** 쪽 읽기의 틀린 값 9개 가운데 여섯은 도번의 글자 오독입니다. `LJT01.06`을 `LJTO106`으로, `LJT05.34`를 `LJT05_34`로, `LJT04.47`을 `LJIT04.47`로, `DJZ-21`을 `DJZ-18`로 읽은 식이고, Tesseract가 틀린 방식(점 빠짐, J와 I)과 같은 종류입니다. 나머지는 재질 `HT200`을 도번으로 읽은 것 하나, 재질을 뭉개 읽은 것 하나, 비례 `1:3`을 `2`로 읽은 것 하나입니다. 칸이 없는데 읽은 7개 가운데 여섯은 비례 칸이 빈 도면에서 `1:2`, `2:1`, `1:1`을 읽은 것으로, 질문에 "상세도 옆의 2:1 같은 뷰 배율은 쓰지 말라"고 적었는데도 그랬습니다. 자름에서는 도면 없이 표제란만 보니 뷰 배율을 덜 가져왔지만(7 → 2), 합비공대 양식의 큰 칸에 든 재질(`HT200`, `HT150`)을 도번으로 읽은 것이 넷 생겼습니다.

**두 읽기가 같은 값을 낸 경우.** 같은 칸을 Tesseract와 Claude가 같은 값으로 읽은 것은 쪽과 자름 모두 17개였고 17개 모두 맞았습니다(95% 구간 하한 82%). 다만 이것은 결과를 본 뒤 같은 61장에서 센 것이라, "둘이 같으면 믿는다"는 규칙의 성능은 아직 재지 않았습니다.

**하네스가 틀렸던 곳.** 첫 실행([40207800589](https://github.com/sokldjs554/fitwitness/actions/runs/40207800589))은 읽기 하나에 모델 호출 한 번만 허용했습니다. 그래서 첫 출력이 스키마에 맞지 않으면 클라이언트가 한 번 고쳐 묻는 것이 막혀, 13개 읽기가 빈 채로 끝났습니다. 그 13쪽을 다시 읽었고([40208747697](https://github.com/sokldjs554/fitwitness/actions/runs/40208747697)), 그중 4쪽은 고쳐 묻기의 예약이 쪽당 상한 $0.02를 넘어 또 막혀서 상한을 $0.04로 올려 읽었습니다([40208989393](https://github.com/sokldjs554/fitwitness/actions/runs/40208989393), [40209087006](https://github.com/sokldjs554/fitwitness/actions/runs/40209087006)). 첫 출력이 맞지 않은 까닭은 모델이 칸 객체를 깨진 문자열(`<parameter name="value">null`)로 낸 것입니다. 질문과 스키마는 바꾸지 않았습니다. 표는 쪽마다 하네스에 막히지 않은 마지막 읽기로 셌고, 첫 실행 그대로의 숫자도 기록(`first_run_as_read`)에 남겼습니다. 한 쪽(`903c8afe`)은 고쳐 물은 뒤에도 상자를 픽셀 좌표로 돌려줘 자르지 못했고 비례를 놓쳤습니다.

**읽는 법.** 같은 쪽에서 Claude는 Tesseract보다 도번을 거의 두 배, 재질을 두 배 읽었고, 비례는 0에서 32~34가 됐습니다. 대신 틀린 값과 칸이 없는데 읽은 값도 늘었습니다(Tesseract 6건, Claude 쪽 16건, 자름 8건). 그래서 이 읽기도 Tesseract의 읽기처럼 "확인 필요"인 관찰이어야 하고, 일치를 만들 수 없습니다. 61장은 거의 한 교재의 쪽이고 한 번씩만 읽었습니다(반복 없음). 이 결과를 보고 질문이나 자르기를 고치면, 그 효과는 세 번째로 뽑는 도면으로 재야 합니다. 기록은 `docs/evaluation/title-block-vlm.json`입니다.

## 프롬프트를 바꿔 보면 (2026-10-27)

틀린 값을 줄이려고 프롬프트를 바꿔 봤습니다. 홀드아웃 1(27장)을 dev, 홀드아웃 2(34장)를 test로 나눴고, 변형은 dev의 오류만 보고 만들었습니다. dev의 오류는 표제란에 없는 척도를 상세도 옆 비율에서 가져온 것(3건), 쪽 전체 해상도에서 O와 0, I와 1을 헷갈린 것(자른 표제란 읽기에서는 맞음), 아예 못 읽은 것이었습니다.

- **변형 `label`.** 칸마다 인쇄된 라벨(图号·材料·比例, 도번·재질·척도)을 값과 함께 `visible_text`에 옮기게 했습니다. 도번의 O/0, I/1을 자리로 구분하라고 쓰고, 라벨이 있는 칸이 없으면 null로 두게 했습니다.
- **인용 검사(grounded).** `visible_text`에 그 칸의 라벨 낱말과 값이 함께 있을 때만 값을 남깁니다. 검색 질의 읽기에서 인용이 없는 제안을 버리는 것과 같은 규칙이고, 호출 없이 같은 출력에서 계산합니다.
- **선택 규칙.** 호출 전에 커밋(`a634803`)했습니다. dev에서 `정답 − 2 × (틀린 값 + 칸이 없는데 읽은 값)`이 가장 큰 (변형, 읽기)를 고르고, 그것으로 test를 한 번 읽습니다. 기준선이 이기면 test는 읽지 않습니다.
