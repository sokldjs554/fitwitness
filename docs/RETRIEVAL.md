# 도면 검색 실험과 실행 경로

기존 도번·BM25 검색에 실제 E5 의미 검색과 OpenCLIP 이미지 검색을 연결했습니다. 공개 무료 체험은 기존 규칙·도번·키워드 엔진이며, 실험실의 복합 검색 결과는 별도 PostgreSQL 작업 환경에서 측정한 기록입니다. 공개 서버에 모델 가중치를 포함하거나 방문자의 요청으로 유료 API를 실행하지 않습니다.

## 구현 범위

- `retrieval/indexing.py`는 원본에서 추출된 사실·제목·도번과 PNG만 읽습니다. 정답 디렉터리를 읽지 않습니다.
- 두 임베딩을 모두 생성한 뒤 한 transaction에서 저장합니다. 인코딩 실패·근거 변경·테넌트 불일치 때 일부 색인을 게시하지 않습니다.
- 모델 revision·파일 SHA-256을 `retrieval/models.json`에 고정했습니다. worker는 hash 검사 후 로컬 모델만 로드합니다. 임의 벡터를 실제 모델 결과로 대체하지 않습니다.
- 검색은 현재 tenant와 고정 snapshot의 승인된 개정만 대상으로 합니다. 입력 전후 snapshot을 확인하고, 사실 변경 시 벡터를 지웁니다. 모델 해시가 다르거나 일부 색인이 없으면 명시적으로 실패합니다.
- worker는 `FITWITNESS_ENCODERS=pretrained`일 때만 모델을 로드합니다. 같은 LangGraph 경로와 typed 검색 도구를 사용합니다. 일반 공개 환경의 기본값은 `off`입니다.
- 이 색인은 작은 코퍼스의 **정확한 cosine 검색**입니다. HNSW/IVFFlat ANN이나 대규모 검색 부하 검증을 했다는 뜻은 아닙니다.

## 작업 환경에서 재현

PostgreSQL+pgvector, 프로젝트 Python 의존성, 기존 tenant의 자료가 필요합니다. 텍스트·이미지 모델을 함께 메모리에 올리므로 무료 웹 인스턴스에서 켜지 않습니다.

```bash
uv sync --frozen --extra dev --extra models
export PYTHONPATH=src
# FITWITNESS_DATABASE_URL은 본인의 작업용 PostgreSQL 연결을 환경 변수로 설정
uv run python scripts/setup.py
uv run python scripts/download_encoders.py
uv run python -m fitwitness.retrieval.indexing --tenant YOUR_EXISTING_TENANT
FITWITNESS_ENCODERS=pretrained uv run python -m fitwitness.runtime.worker \
  --tenant YOUR_EXISTING_TENANT --run YOUR_QUEUED_RUN_ID
```

평가는 빈 결과 디렉터리와 별도 tenant를 생성하며 기존 결과에 덮어쓰지 않습니다. 유료 LLM 키가 필요하지 않습니다.

```bash
uv run python -m fitwitness.evaluation.retrieval --output artifacts/retrieval-new
```

## 평가 설계

150개 활성 합성 도면, 30개 family 중 고정 test6개 family의 24개 질문을 사용합니다. 도번·설명·이미지·설명+이미지 각각6개입니다. 같은 질문에서 도번+BM25, E5, OpenCLIP, 네 채널 RRF를 비교하고3회 반복합니다. 총288번 검색이며 독립288개 질문은 아닙니다. 모델·RRF 상수60·top10을 test 결과에 맞춰 선택하지 않았습니다.

텍스트 질문은 종류와 폭만 정답 기준으로 사용합니다. 이미지·복합 질문은 보이는 구멍 간격까지 포함합니다. 재질이나 조립 적합성 정답과 구분합니다. 도면에서 잘라 크기·회전을 바꾼 이미지이므로 독립 촬영·외부 자료 평가로 해석하지 않습니다. PDF·원본 PNG·변형 질문 PNG의 해시와 변형 방식이 protocol에 남습니다.

입력 모달리티가 없는 방식은 빈 결과를 반환합니다. 전체 평균만 보면 이미지 질문에서 키워드 방식이 불리하므로 질문 유형별 지표를 같이 표시합니다. 검색 지연은 모델 로드·색인 시간을 제외한 query encode+DB+fusion 전체 시간입니다. 모델 로딩과 색인 시간은 별도 필드에 기록합니다. 세 반복의 순위를 유지하고, 화면에는 반복1의 후보와 채널별 점수를 표시합니다.

## 검토에서 발견한 실패

첫 실행은 모델 목록에 다운로드 임시 파일이 들어가404가 발생해 추론 전 종료됐습니다. 공식 파일명만 고정하고 회귀 검증했습니다. 두 번째 실행 중, 점수를 보기 전에 설명 질문의 정답 기준에 질문에 없는 구멍 간격이 포함된 문제를 확인했습니다. 실패 재현 후 v2에서 유형별 정답 기준으로 수정했습니다. 이전 protocol은 유효한 비교 성과로 사용하지 않습니다.

아래 v2는 검색 채널 비교입니다. 후속 재정렬·VLM은 별도 실험이며 CAD 거리·외부 산업 자료·대규모 색인·의도 일반화는 미완료입니다.

## 이미지 채널 비교 — DINOv2 vs OpenCLIP (2026-10-23)

공고의 "이미지의 형상으로 검색"에 가장 가까운 채널은 OpenCLIP 하나였고 v2에서 이미지 질의 Recall@5가 11.1%였습니다. 자기지도 이미지 인코더가 도면의 잘린 그림을 더 잘 찾는다는 다른 연구의 보고(DINOv2 계열)를 같은 코퍼스에서 확인하려고, `facebook/dinov2-small`의 CLS 토큰을 두 번째 이미지 채널(`image_dino`)로 색인하고 수동 workflow [`image-channel-evaluation.yml`](../.github/workflows/image-channel-evaluation.yml)로 다섯 방식을 비교했습니다. 모델은 [`encoder-pin`](../.github/workflows/encoder-pin.yml)이 찍어 준 해시로 고정했습니다. [Actions 39898396591](https://github.com/sokldjs554/fitwitness/actions/runs/39898396591), 코드 `fa507f7`, [기록](evaluation/image-channel.json).

질의는 test family 4개의 36개(도번, 도번 변형, 도번 오타, 설명, 이미지, 설명+이미지 각 6개) × 3회입니다. v2 뒤에 도번 변형·오타 질의가 추가되어 **전체 평균은 v2와 나란히 둘 수 없고**, 질문 유형별 수치만 비교할 수 있습니다. 질의 그림은 v2와 같은 변형(자르기, 240×143 축소, 3도 회전)입니다.

## 질의를 모델이 읽어 조건으로 (2026-10-23)

지금까지 검색 질의의 치수 조건은 `retrieval/pipeline.extract_requirements`의 패턴이 읽었습니다. 치수 낱말, 숫자, 단위가 그 순서로 있어야 읽히고, "폭은 65mm", "두께 4mm 이상", "구멍 사이 거리 40", "65 millimetres wide", "AL6061 말고"는 못 읽거나 잘못 읽습니다(마지막 것은 빼 달라는 재질을 원하는 재질로 읽습니다). `retrieval/understanding.py`는 모델(Claude Haiku 4.5)이 질의 전체를 읽고 부품 종류, 치수 구간(이상·이하는 한쪽이 열린 구간), 재질, 빼 달라는 재질을 제안하게 하되, 제안마다 질의에서 그대로 따온 인용을 붙이게 하고 인용이 질의에 없으면 버립니다. 모델은 질의에 없는 조건을 더할 수 없습니다. 패턴 읽기는 그대로 두고, 근거 있는 제안이 패턴이 읽은 글귀를 포함하는 더 긴 글귀에서 왔을 때만 그 항목을 대신하며("두께 4mm 이상"이 "두께 4mm"를), 같은 필드에서 그 조건 없이 값이 다르면 패턴의 값을 두고 불일치로 기록합니다. `SearchRequest.understanding="model"`로 켜는 선택 사항이고 기본은 패턴입니다. 그래프의 intent 노드가 `understood` 이벤트로 제안·버린 것·바꾼 것을 남기고, retrieve 노드는 그렇게 정해진 조건으로 후보를 정렬합니다.

**측정.** `evaluation/query_understanding.py`와 수동 워크플로 `query-understanding-evaluation`입니다. family마다 기준 도면의 gold에서 문장 열 가지를 만듭니다. 범위(에서 ... 사이), cm 단위, 하한(이상), 단위 없는 숫자, 영어, 조사(폭은), 정형(패턴이 읽는 대조군), 재질 제외(말고), 단위를 말로(밀리미터), 띄어쓰기 없음(미리). 기대 조건은 필드와 mm 구간, 종류, 재질, 제외 재질이고, 패턴 읽기와 모델을 병합한 읽기를 필드 단위로 채점합니다. 같은 질의를 복합 검색(도번·BM25·E5)에 넣고 각 읽기의 조건으로 정렬해, gold가 질의의 조건을 모두 만족하는 도면을 정답으로 Recall@5를 잽니다. RRF 상위 20개 풀의 재현율이 어느 정렬이든 넘을 수 없는 상한입니다. dev 6 family를 먼저 돌려 보고, 아무것도 바꾸지 않은 채 test 6 family를 한 번 돌렸습니다. 호출당 예약 $0.02, 묶음 상한 $0.15입니다. 문장과 프롬프트는 호출 전에 썼고 dev 뒤에도 바꾸지 않았습니다. 기록은 [query-understanding.json](evaluation/query-understanding.json)에 있습니다.

**읽는 법.** 패턴은 열 가지 가운데 cm 단위와 정형 대조군만 읽습니다(12/60). 모델은 두 분할에서 60문장을 모두 기대 조건대로 읽었고, 근거가 없어 버린 제안도, 패턴과의 불일치도 없었습니다. 분할마다 바꾼 12개는 하한 문장의 닫힌 구간을 연 것 6개와 제외 문장에서 패턴이 원하는 재질로 읽은 것을 뺀 것 6개입니다. 검색에서는 모델 조건 정렬이 패턴 조건 정렬보다 두 분할 모두 17.2%p 높고 풀의 상한(74.5%, 79.2%)에 3~4%p 모자랍니다. 남은 차이는 읽기가 아니라 후보 풀에 있습니다. 범위 문장은 모델이 읽어도 23.3%인데, 설명문으로 된 질의에 의미 채널이 같은 종류의 도면을 풀에 넣지 못하기 때문입니다. 하한 문장은 정답이 많아(두께가 그 이상인 같은 종류 도면 전부) Recall@5가 구조적으로 낮습니다. 재질 제외 문장의 이득은 제외를 적용한 것이 아니라 패턴이 잘못 세운 재질 조건을 없앤 데서 옵니다. 검증기에 부정이 없어 제외 재질은 기록에만 남고 정렬에는 쓰이지 않습니다. 종류도 도면의 사실이 아니라 정렬에 쓰이지 않습니다.

**솔직하게 적어야 할 것.** 문장 열 가지는 제가 같은 gold에서 만든 틀이고, 60문장은 틀 10개에 family의 숫자 6벌을 넣은 것이지 독립된 문장 60개가 아닙니다. 60/60의 95% 구간 94.0%는 그 독립성을 가정한 값이라 실제보다 좁습니다. 이 측정이 보여 주는 것은 "모델이 이 열 가지 쓰기 방식을 패턴보다 잘 읽고, 그 읽기가 질의에 없는 조건을 더하지 못하는 채로 검색 순서를 올린다"이지, 현장의 질의를 읽는다는 것이 아닙니다. 질의 하나에 $0.002, 1.4 s입니다. 두 묶음 합계 $0.24565는 누적 API 비용과 따로 적습니다.
