# 도면 검색 실험과 실행 경로

기존 도번·BM25 검색에 실제 E5 의미 검색과 OpenCLIP 이미지 검색을 연결했습니다. 공개 무료 체험은 기존 규칙·도번·키워드 엔진이며, 실험실의 복합 검색 결과는 별도 PostgreSQL 작업 환경에서 측정한 기록입니다. 공개 서버에 모델 가중치를 포함하거나 방문자의 요청으로 유료 API를 실행하지 않습니다.

## 구현 범위

- `retrieval/indexing.py`는 원본에서 추출된 사실·제목·도번과 PNG만 읽습니다. 정답 디렉터리를 읽지 않습니다.
- 도번 정규화(`retrieval/drawing_number.py`)가 읽는 표기: 하이픈·공백·밑줄·점과 모든 종류의 대시(`FW–000–4`, `FW.000.4`), 영문 O·I·l·S·B를 숫자로 읽은 입력(신뢰도를 깎음), 0 패딩과 묶음이 다른 같은 번호(`FW-0004`, `FW-0-4`는 `FW-000-4`를 0.9로), 번호 뒤 개정 문자(`FW-000-4A`는 `FW-000-4`를 0.9로, 시리즈 전체가 아님). 번호 뒤에 다른 접두어가 오면(`FW-000-4 BS-120`) 새 참조로 나눕니다. 2026-10-30 전에는 `BS`가 숫자 85로 읽혀 두 번호가 하나로 합쳐졌고, 대시·점은 0건, 개정 문자는 시리즈로 잘렸습니다(감사에서 재현, 시험으로 고정). 게이트의 도번 변형 사례는 이 표기들을 아직 담지 않아, 새 표기의 정확도는 `tests/unit/test_drawing_number.py`의 사례로만 확인합니다.
- 두 임베딩을 모두 생성한 뒤 한 transaction에서 저장합니다. 인코딩 실패·근거 변경·테넌트 불일치 때 일부 색인을 게시하지 않습니다.
- 모델 revision·파일 SHA-256을 `retrieval/models.json`에 고정했습니다. worker는 hash 검사 후 로컬 모델만 로드합니다. 임의 벡터를 실제 모델 결과로 대체하지 않습니다.
- 검색은 현재 tenant와 고정 snapshot의 승인된 개정만 대상으로 합니다. 입력 전후 snapshot을 확인하고, 사실 변경 시 벡터를 지웁니다. 모델 해시가 다르거나 일부 색인이 없으면 명시적으로 실패합니다.
- worker는 `FITWITNESS_ENCODERS=pretrained`일 때만 모델을 로드합니다. 같은 LangGraph 경로와 typed 검색 도구를 사용합니다. 일반 공개 환경의 기본값은 `off`입니다.
- 이 색인은 작은 코퍼스의 **정확한 cosine 검색**입니다. HNSW/IVFFlat ANN이나 대규모 검색 부하 검증을 했다는 뜻은 아닙니다.

## 작업 환경에서 재현

PostgreSQL+pgvector, 프로젝트 Python 의존성, 기존 tenant의 자료가 필요합니다. 텍스트·이미지 모델을 함께 메모리에 올리므로 무료 웹 인스턴스에서 켜지 않습니다.

```bash
uv sync --frozen --extra dev --extra models
export PYTHONPATH=src
# FITWITNESS_DATABASE_URL은 본인의 작업용 PostgreSQL 연결을 환경 변수로 설정
uv run python scripts/setup.py
uv run python scripts/download_encoders.py
uv run python -m fitwitness.retrieval.indexing --tenant YOUR_EXISTING_TENANT
FITWITNESS_ENCODERS=pretrained uv run python -m fitwitness.runtime.worker \
  --tenant YOUR_EXISTING_TENANT --run YOUR_QUEUED_RUN_ID
```

평가는 빈 결과 디렉터리와 별도 tenant를 생성하며 기존 결과에 덮어쓰지 않습니다. 유료 LLM 키가 필요하지 않습니다.

```bash
uv run python -m fitwitness.evaluation.retrieval --output artifacts/retrieval-new
```

## 평가 설계

150개 활성 합성 도면, 30개 family 중 고정 test6개 family의 24개 질문을 사용합니다. 도번·설명·이미지·설명+이미지 각각 6개입니다. 같은 질문에서 도번+BM25, E5, OpenCLIP, 네 채널 RRF를 비교하고 3회 반복합니다. 총 288번 검색이며 독립 288개 질문은 아닙니다. 모델·RRF 상수 60·top10을 test 결과에 맞춰 선택하지 않았습니다.

텍스트 질문은 종류와 폭만 정답 기준으로 사용합니다. 이미지·복합 질문은 보이는 구멍 간격까지 포함합니다. 재질이나 조립 적합성 정답과 구분합니다. 도면에서 잘라 크기·회전을 바꾼 이미지이므로 독립 촬영·외부 자료 평가로 해석하지 않습니다. PDF·원본 PNG·변형 질문 PNG의 해시와 변형 방식이 protocol에 남습니다.

입력 모달리티가 없는 방식은 빈 결과를 반환합니다. 전체 평균만 보면 이미지 질문에서 키워드 방식이 불리하므로 질문 유형별 지표를 같이 표시합니다. 검색 지연은 모델 로드·색인 시간을 제외한 query encode+DB+fusion 전체 시간입니다. 모델 로딩과 색인 시간은 별도 필드에 기록합니다. 세 반복의 순위를 유지하고, 화면에는 반복 1의 후보와 채널별 점수를 표시합니다.

## 검토에서 발견한 실패

첫 실행은 모델 목록에 다운로드 임시 파일이 들어가 404가 발생해 추론 전 종료됐습니다. 공식 파일명만 고정하고 회귀 검증했습니다. 두 번째 실행 중, 점수를 보기 전에 설명 질문의 정답 기준에 질문에 없는 구멍 간격이 포함된 문제를 확인했습니다. 실패 재현 후 v2에서 유형별 정답 기준으로 수정했습니다. 이전 protocol은 유효한 비교 성과로 사용하지 않습니다.

아래 v2는 검색 채널 비교입니다. 후속 재정렬·VLM은 별도 실험이며 CAD 거리·외부 산업 자료·대규모 색인·의도 일반화는 미완료입니다.

## 이미지 채널 비교 — DINOv2 vs OpenCLIP (2026-10-23)

공고의 "이미지의 형상으로 검색"에 가장 가까운 채널은 OpenCLIP 하나였고 v2에서 이미지 질의 Recall@5가 11.1%였습니다. 자기지도 이미지 인코더가 도면의 잘린 그림을 더 잘 찾는다는 다른 연구의 보고(DINOv2 계열)를 같은 코퍼스에서 확인하려고, `facebook/dinov2-small`의 CLS 토큰을 두 번째 이미지 채널(`image_dino`)로 색인하고 수동 workflow [`image-channel-evaluation.yml`](../.github/workflows/image-channel-evaluation.yml)로 다섯 방식을 비교했습니다. 모델은 [`encoder-pin`](../.github/workflows/encoder-pin.yml)이 찍어 준 해시로 고정했습니다. [Actions 39898396591](https://github.com/sokldjs554/fitwitness/actions/runs/39898396591), 코드 `fa507f7`, [기록](evaluation/image-channel.json).

질의는 test family 4개의 36개(도번, 도번 변형, 도번 오타, 설명, 이미지, 설명+이미지 각 6개) × 3회입니다. v2 뒤에 도번 변형·오타 질의가 추가되어 **전체 평균은 v2와 나란히 둘 수 없고**, 질문 유형별 수치만 비교할 수 있습니다. 질의 그림은 v2와 같은 변형(자르기, 240×143 축소, 3도 회전)입니다.

| 방식 | 이미지 질의 Recall@5 | 설명+이미지 | 설명 | 도번·변형·오타 | 전체(36개 질의) | p50 |
|---|---:|---:|---:|---:|---:|---:|
| OpenCLIP만 | 11.1% | 11.1% | 0% | 0% | 3.7% | 50 ms |
| DINOv2만 | **37.5%** | **37.5%** | 0% | 0% | 12.5% | 49 ms |
| 복합 RRF + OpenCLIP (기존) | 11.1% | 9.7% | 12.5% | 100% | 55.6% | 75 ms |
| 복합 RRF + DINOv2 | **37.5%** | **26.4%** | 12.5% | 100% | 62.7% | 76 ms |
| 복합 RRF + 둘 다 | 20.8% | 5.6% | 12.5% | 100% | 56.5% | 77 ms |

**읽기.** 같은 그림에서 DINOv2가 OpenCLIP보다 원본 도면을 더 자주 찾았고, 복합 검색의 이미지 채널을 바꾸면 이미지·설명+이미지 질의만 오르고 나머지는 그대로입니다. 두 이미지 채널을 같은 가중치의 RRF에 함께 넣으면 DINOv2만 쓸 때보다 나빠졌습니다. 약한 채널의 순위가 섞이기 때문으로 보이지만 이 실행 하나로 원인을 확정하지 않습니다.

**한계.** 이미지 질의는 6개 × 3회뿐이고, 질의 그림은 색인된 도면 자체의 변형이라 촬영·스캔·손그림 일반화가 아닙니다. dinov2-small과 CLS 토큰 한 가지 설정이며 미세조정은 없습니다. 이 결과로 기본 검색 채널을 바꾸지 않았고, 더 많은 질의와 외부 도면에서 같은 방향이 보이면 바꿉니다. 사례별 행과 구간은 artifact의 `runs.jsonl.gz`에서 계산할 수 있습니다.

## 질의를 모델이 읽어 조건으로 (2026-10-23)

지금까지 검색 질의의 치수 조건은 `retrieval/pipeline.extract_requirements`의 패턴이 읽었습니다. 치수 낱말, 숫자, 단위가 그 순서로 있어야 읽히고, "폭은 65mm", "두께 4mm 이상", "구멍 사이 거리 40", "65 millimetres wide", "AL6061 말고"는 못 읽거나 잘못 읽습니다(마지막 것은 빼 달라는 재질을 원하는 재질로 읽습니다). `retrieval/understanding.py`는 모델(Claude Haiku 4.5)이 질의 전체를 읽고 부품 종류, 치수 구간(이상·이하는 한쪽이 열린 구간), 재질, 빼 달라는 재질을 제안하게 하되, 제안마다 질의에서 그대로 따온 인용을 붙이게 하고 인용이 질의에 없으면 버립니다. 모델은 질의에 없는 조건을 더할 수 없습니다. 패턴 읽기는 그대로 두고, 근거 있는 제안이 패턴이 읽은 글귀를 포함하는 더 긴 글귀에서 왔을 때만 그 항목을 대신하며("두께 4mm 이상"이 "두께 4mm"를), 같은 필드에서 그 조건 없이 값이 다르면 패턴의 값을 두고 불일치로 기록합니다. `SearchRequest.understanding="model"`로 켜는 선택 사항이고 기본은 패턴입니다. 그래프의 intent 노드가 `understood` 이벤트로 제안·버린 것·바꾼 것을 남기고, retrieve 노드는 그렇게 정해진 조건으로 후보를 정렬합니다.

## 규모: 도면 1천·1만·10만 장 (2026-10-27, 고친 뒤 2026-10-29)

"도면 10만 장이면 어디가 먼저 무너지나"를 재려고 [scripts/scale-search.py](../scripts/scale-search.py)가 합성 도면을 크기별로 새 작업 공간에 넣고, API가 부르는 것과 같은 함수로 시간을 쟀습니다. 도면마다 개정판 하나, 짧은 PDF 대용 바이트, 사실 다섯 개이고, 도번은 `SC-01234-3` 꼴로 다섯 장이 한 family입니다. DB는 같은 기계의 PostgreSQL(pgserver)이라 원격 DB의 네트워크 시간은 들어 있지 않습니다. 모델은 부르지 않습니다.

**먼저 잰 것(고치기 전, 2026-10-27, [기록](evaluation/scale-search-reading-path.json)).** 검색 한 번이 테넌트의 개정판과 사실 전체를 세 번 읽어 pydantic 모델로 바꾸고(요청 전 스냅숏, 검색 안의 코퍼스, 끝의 스냅숏 재확인), 질의마다 BM25 색인을 새로 만들었습니다.

| 도면 수 | 검색 한 번(중앙값) | 코퍼스 한 번 읽기 | 자유 질의 검색 | 메모리 최대 |
|---|---|---|---|---|
| 1,000 | 0.46초 | 0.19초 | 0.7초 | 116 MB |
| 10,000 | 6.3초 | 4.2초 | 10.2초 | 598 MB |
| 100,000 | 84초 | 55초 | 127.5초 | 5.4 GB |

**고친 것.** 검색이 쓰는 것만 한 번의 쪽 단위 읽기로 만들어 두고, 코퍼스가 바뀔 때까지 씁니다(`storage/corpus_state.py`).

- 스냅숏 id는 예전과 같은 값입니다(같은 행 위의 같은 SHA-256). 쪽으로 읽으면서 해시를 이어 가므로 모델 객체를 만들지 않고, 기록된 id와 단위 테스트가 같은 값임을 확인합니다.
- "코퍼스가 바뀌었나"는 DB가 알려 줍니다. `fw_corpus_version`이 테넌트마다 카운터를 두고, 개정판·사실·벡터 표에 쓰는 모든 문장이 같은 트랜잭션에서 카운터를 올립니다(문장 단위 트리거, 행마다가 아니라 문장마다 한 번). 프로세스는 카운터가 자기가 읽을 때의 값이면 읽은 것을 그대로 쓰고, 다르면 다시 읽습니다. 쓰는 코드가 이 카운터를 잊어도 트리거가 올립니다. 커밋되지 않은 쓰기를 본 상태는 기억하지 않고, 읽는 중에 카운터가 움직이면 다시 읽습니다. 다른 프로세스(worker)도 같은 카운터로 판단합니다.
- 도번은 한 번 쪼개 접두어별로 묶어 두고, 한 글자 오타는 편집 거리 1의 후보 문자열을 사전에서 찾습니다(거리를 모든 도번에 재지 않습니다). BM25 색인은 코퍼스가 바뀔 때까지 한 번 만듭니다. 후보로 나가는 도면만 사실을 읽습니다.
- 순위는 예전과 같아야 하므로, 읽는 쪽 경로를 그대로 남겨 두고 같은 질의를 두 경로에 넣어 후보·점수가 같은지 대조합니다(아래 표의 마지막 열과 통합 테스트).

**고친 뒤 ([기록](evaluation/scale-search.json), 질의 10개 × 다섯 형태씩).**

| 도면 수 | 처음 읽기(코퍼스 한 번) | 그 뒤 상태 확인 | 첫 질의(색인 구성) | 도번 질의 중앙값(최대) | 자유 질의 | 메모리 최대 | 옛 경로 같은 질의(순위 같음) |
|---|---|---|---|---|---|---|---|
| 1,000 | 0.22초 | 0.8 ms | 51 ms | 5~8 ms (16 ms) | 9 ms | 72 MB | 0.47초 / 0.35초 (같음) |
| 10,000 | 1.8초 | 0.9 ms | 0.39초 | 45~76 ms (92 ms) | 96 ms | 114 MB | 5.9초 / 4.3초 (같음) |
| 100,000 | 24.0초 | 0.7 ms | 3.4초 | 163~387 ms (614 ms) | 0.50초 | 470 MB | 69초 / 44초 (같음) |

도번 질의의 첫 결과는 쓴 그대로, 소문자·구분자를 바꾼 것, 숫자 자리의 0을 O로 친 것 모두 모든 크기에서 10/10으로 맞았습니다. 앞 글자 S를 5로 친 도번(`5C-…`)은 여전히 0개입니다(정규화가 숫자 자리 안의 글자만 고치는 한계, 규모와 무관). 없는 member를 친 도번(`SC-01234-7`)은 같은 family의 도면이 첫 결과인 비율이 1,000장 8/10, 10,000장 9/10, 100,000장 10/10입니다. 틀린 경우는 한 자리 바꿔치기(전치)로 닿는 다른 family의 도면이 같은 점수로 앞에 선 것이고, 한 글자 오타 일치의 정의가 그렇습니다. 메모리와 시간은 기계 하나의 값이고 "옛 경로" 열은 같은 실행에서 스냅숏을 한 번 덜 읽은 상태라 위 고치기 전 표의 84초·127초보다 짧습니다.

**남은 한계.**

- **처음 읽기가 10만 장에서 24초입니다.** 코퍼스가 바뀐 뒤 처음 오는 검색(과 처음 오는 실행)이 그 시간을 내고, 프로세스마다 한 번씩입니다. 그동안 같은 테넌트의 다른 요청은 기다립니다. 도면을 하루에 몇 번 올리는 운영에서는 올릴 때마다 다시 지불하므로, 올리는 쪽에서 미리 데워 두거나 증분으로 갱신해야 합니다. 증분 갱신은 하지 않았습니다.
- 메모리 470 MB는 10만 장일 때의 프로세스 최대입니다(도면 텍스트와 BM25 색인). 무료 인스턴스(512 MB)는 그 규모를 버티지 못합니다.
- 도번 질의가 10만 장에서 0.2~0.4초인 것은 접두어가 하나(`SC`)인 합성 코퍼스에서 같은 접두어의 도번을 훑는 비용입니다. 접두어가 여럿인 실제 도면에서는 줄어들 것으로 보지만 재지 않았습니다.
- **의미(텍스트 벡터)·이미지 채널은 아래 별도 측정이 있고, 실제 인코더와 품질은 재지 않았습니다.** 위 표는 도번과 BM25 두 채널입니다.
- 로컬 DB라 원격 DB의 네트워크 시간(상태 확인 한 번 = 왕복 한 번)은 들어 있지 않습니다. 합성 코퍼스이고 실제 도면 10만 장이 아닙니다.

### 벡터 채널 (의미·이미지), 10만 장 (2026-10-29)

[scripts/scale-vectors.py](../scripts/scale-vectors.py)가 같은 방식으로 도면마다 텍스트 벡터 384개와 이미지 벡터 512개를 **무작위 값으로** DB가 쓰게 하고(사실은 없음), 실제 검색 함수에 의미·이미지 채널을 켜서 잽니다. 그래서 이 숫자는 지연과 메모리뿐이고 검색 품질이 아니며, 실제 인코더(E5, OpenCLIP: 질의 하나에 CPU로 수십 ms)의 시간은 들어 있지 않습니다. 이 표는 ANN 색인 없이 정확 검색(행을 훑음)으로 잰 것이고, 기록은 [scale-vectors.json](evaluation/scale-vectors.json)입니다. 같은 날 밤 HNSW 색인을 더한 뒤의 측정은 아래 절에 있습니다.

| 도면 수 | 처음 읽기(코퍼스 한 번) | 의미 채널 검색(중앙값) | 이미지 채널 검색 | 도번+BM25+의미+이미지 | 메모리 최대 |
|---|---|---|---|---|---|
| 10,000 | 1.0초 | 87 ms | 130 ms | 226 ms (최대 296 ms) | 100 MB |
| 100,000 | 8.9초 | 0.87초 | 1.3초 | 2.5초 (최대 3.7초) | 510 MB |

두 가지를 찾아 고쳤습니다.

- **검색마다 모든 도면의 벡터 색인을 확인했습니다.** 검색 앞에서 "모든 활성 도면이 이 인코더로 만든 벡터를 가졌는지"를 전부 읽어 확인해서, 10만 장에서 3.0초가 이것이었습니다. 벡터 쓰기는 코퍼스 변경 카운터를 올리므로 이 확인은 코퍼스 상태마다 한 번이면 되어 캐시했습니다. 이 확인의 비용은 `scale-vectors.json`의 `index_check_ms` 2,991 ms이고, 고치기 전의 검색 전체 시간은 따로 기록하지 않았습니다.
- **대량 적재 직후 첫 벡터 검색이 10만 장에서 115초였습니다.** 두 번째는 1초였습니다. 느린 동안 DB는 하나의 백엔드가 대기 이벤트 없이 일하고 있었고(CPU), 원인은 방금 적재한 행에 대한 통계가 아직 없어서 플래너가 나쁜 계획을 고른 것으로 보입니다. 적재 직후 `ANALYZE fw_vectors`(0.3초)를 하면 첫 검색이 0.83초였고, 하지 않은 기록은 [scale-vectors-without-analyze.json](evaluation/scale-vectors-without-analyze.json)에 남아 있습니다. 일괄 색인 CLI(`python -m fitwitness.retrieval.indexing`)가 끝에서 이제 이 통계 갱신을 합니다. 원인을 계획으로 직접 확인한 것은 아니고 통계를 갱신하면 사라진다는 대조입니다. 같은 문제를 `unnest` 조인으로 피해 보려던 시도는 첫 검색이 19분으로 더 나빠 되돌렸습니다(이 시도의 기록은 저장소에 없습니다).

남은 것(이 측정 시점): 이미지 채널이 1.3초대인 것은 512차원 10만 행을 훑는 값이고, 더 줄이려면 ANN 색인(HNSW)이 필요했습니다. 활성 도면 id 10만 개를 질의마다 배열로 보냅니다. 인코더 시간과 품질은 이 측정에 없습니다.

### HNSW 색인 (2026-10-29 밤)

채널마다 pgvector HNSW 색인을 두었습니다(`storage/repository.py`의 `HNSW_CHANNELS`: text 384, image 512, image_dino 384, 코사인 거리). `embedding` 열은 너비가 고정되어 있지 않아서 색인은 "그 채널이고 그 너비인 행"만 담는 부분 표현식 색인이고, 다른 너비의 벡터(테스트는 3차원을 씁니다)는 저장은 되되 색인 밖에 있어 정확 검색으로 답합니다. 검색문은 채널과 너비를 매개변수가 아니라 글자로 적어야 플래너가 부분 색인과 맞출 수 있고, 거리 식은 한 번만 계산해 별칭으로 정렬하며, 서버 쪽 prepared statement 없이 매번 계획합니다(아래 "재다 겪은 것"). 후보 수(`hnsw.ef_search`)는 요청한 행 수 이상으로 두고 기본 400입니다(`FITWITNESS_HNSW_EF_SEARCH`). `migrate()`가 색인을 만들므로 운영에서는 색인이 있는 채로 적재되고, 대량 적재는 색인을 지우고 적재한 뒤 다시 만드는 쪽이 빠릅니다(아래 수치). 통합 테스트는 1,500장 테넌트에서 플래너가 색인을 타는 것과, 60장에서는 기본 키 경로로 정확 검색과 같은 답을 내는 것을 확인합니다.

[scripts/scale-vectors.py](../scripts/scale-vectors.py)를 같은 무작위 벡터로 다시 돌렸습니다(pgvector 0.6.2, 로컬 PostgreSQL 16, 기록 [scale-vectors-hnsw.json](evaluation/scale-vectors-hnsw.json)). 정확 검색의 정답과 비교한 재현율@50은 질의 8개의 평균입니다.

| 도면 수 | 색인 만들기(적재 뒤, 두 채널) | 색인 크기 | 색인 있는 채로 1,000장(벡터 2,000개) 더 넣기 | 정확 검색(색인 전 문장) | HNSW ef 40 / 100 / 200 / 400 (의미 채널) | 재현율@50 ef 40 / 100 / 200 / 400 |
|---|---|---|---|---|---|---|
| 10,000 | 6.4초 | 20 + 26 MB | 14.8초 | 88 ms (이미지 154 ms) | 68 / 75 / 86 / 79 ms | 0.57 / 0.71 / 0.84 / 0.93 (이미지 0.56 / 0.72 / 0.83 / 0.91) |
| 100,000 | 131초 (maintenance_work_mem 1 GB) | 217 + 289 MB | 28.4초 | 1.23초 (이미지 2.67초) | 470 / 436 / 452 / 470 ms (이미지 441 / 421 / 507 / 521 ms) | 0.22 / 0.29 / 0.43 / 0.57 (이미지 0.18 / 0.28 / 0.37 / 0.55) |

네 채널(도번+BM25+의미+이미지) 검색 한 번의 중앙값은 10만 장에서 2.5초(색인 전) → 1.15초, 최대 3.7초(`scale-vectors.json`) → 2.5초(`scale-vectors-hnsw.json`)입니다. 10만 장에서 ef 40은 요청한 50행보다 적게(37~41행) 돌려줍니다. pgvector의 기본값 40을 그대로 쓰면 안 되는 이유입니다.

**읽는 법.** 시간은 10만 장에서 2.6~5배 줄었지만 재현율은 낮습니다. 무작위 벡터는 HNSW에 가장 불리한 분포입니다. 군집이 없고 모든 점의 거리가 비슷해서 그래프를 따라가도 정답에 가까워지지 않습니다. 실제 인코더가 만든 벡터는 군집이 있어 같은 ef에서 훨씬 높은 재현율이 보통이지만, **그것은 여기서 재지 않았습니다.** 실제 E5·OpenCLIP 벡터 10만 개로 재현율을 재는 일이 남아 있고, 10만 장의 의미 있는 텍스트가 필요합니다(합성 제목 "part SC-00001-0"을 인코더에 넣으면 그것도 퇴화된 분포입니다). 그래서 이 숫자는 색인의 비용(만드는 시간, 크기, 넣는 속도)과 이 분포에서의 근사 정도이지 검색 품질이 아닙니다.

**재다 겪은 것.** 첫 실행은 전체 테스트가 같은 기계에서 돌던 중에 재서 시간을 버렸습니다. 두 번째 실행에서는 10만 장의 재현율 루프가 모든 ef에서 재현율 1.0에 1.2초로 정확 경로처럼 동작했는데, 같은 함수를 바로 뒤에 다시 돌리니 색인을 탔습니다. 원인은 확인하지 못했습니다(풀의 연결에 남은 서버 쪽 prepared statement의 일반 계획을 의심합니다). 검색문을 prepared statement 없이 실행하도록 바꾼 세 번째 실행이 위 표이고, 이 실행에서는 10만 장도 일관되게 색인을 탔습니다. 두 번째 실행의 기록은 남기지 않았습니다.
