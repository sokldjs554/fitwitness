# FitWitness 설계 검토안

작성: 2026-10-04 (한국 시간) · 대상: 텔어스 AI Research Engineer - Agents & Workflows

상태: 설계안. 제품 구현·성능 실험·원격 저장소 생성·배포는 아직 수행하지 않았다. 아래 수치와 동작은 달성 결과가 아닌 구현 범위와 검증 목표다.

## 1. 만들 결과물

**FitWitness는 자연어·이미지로 도면을 찾고, 후보를 쓰면 안 되는 결정적 근거를 찾아 비교하며, 도면 변경 이후에는 이전 판단을 다시 검증하는 Agent 시스템이다.**

대상 사용자는 도번을 모르는 제조 현장의 구매·정비·생산 담당자다. 면접관에게는 검색 결과보다 Agent가 추가 근거를 구하고 판단을 수정하는 과정, 그 효과를 입증하는 실험을 보여준다.

사용자 요구: 흔한 프로젝트 제외, 공고의 기술 역량 전체 활용, 기존 프로젝트와 별개의 새 GitHub 저장소, 실제 체험 가능한 데모. 완성 판정에는 코드, API, UI, 영속화, 예외 처리, 회귀, 문서와 실제 배포 상태의 일치를 포함한다.

설계 가정: 제조 도메인 하나에 집중한다. 의료 보험금 지급은 공고의 사업 사례이며 별도 제품 구현 요구는 아니므로 범위에 포함하지 않는다. 장기 실행·추출·기준 적용·상태 복구 역량은 제조 흐름 안에서 구현한다. 한글 UI·README를 기본으로 하며 자체 코드 라이선스는 Apache-2.0을 제안한다. 의존 라이선스는 별도 고지한다.

기능을 통해 학사 학위나 실무 경력 1년을 대체·증명했다고 주장하지 않는다. 실제 제출 자료에서 개인 이력과 프로젝트 성과를 구분한다.

## 2. 조사와 선택

2026-10-04 공식 제품 설명을 확인했다. 이는 공급사 기능 설명 조사이며 제품을 직접 사용한 성능 비교가 아니다.

| 후보 | 이점 | 한계와 선택 |
|---|---|---|
| 자연어·이미지 CAD 검색 | 공고의 제조 사례와 직접 연결 | 이미 유사 제품이 있어 이것만으로 차별화하기 어렵다 |
| 도면 개정판 비교와 변경 보고서 | 변경을 시각적으로 보여주기 좋다 | 기존 비교 제품과 겹치며 Agent의 자율적 탐색을 보여주기 어렵다 |
| 반례 탐색과 변경 후 판단 재검증 | Retrieval·Agent·Evals·복구를 한 사용자 흐름으로 연결 | 평가 데이터와 근거의 출처 설계가 어렵지만 포트폴리오의 중심으로 선택한다 |

공식 설명에서 Leo AI는 형상·기능·자연어 검색, DARE Research는 DWG 형상 유사 검색, Glypad Change Intelligence는 치수·공차·형상·BOM의 개정 차이 분석을 제시한다. 따라서 검색이나 개정 비교 자체를 독창적 발명이라고 표현하지 않는다.

차별화 가설은 다음 세 가지를 결합하고 재현 가능한 실험으로 공개하는 데 있다. 이 조합의 세계 최초성이나 경쟁 제품 대비 우월성은 주장하지 않는다.

1. **반례 우선 탐색:** 상위 후보가 틀릴 수 있는 치수·재질·개정 조건을 찾아 다음 검색 도구를 선택한다.
2. **판단의 근거 연결:** 추천뿐 아니라 탈락·보류 판단도 도면 페이지와 영역, 개정판, 원문에 연결한다.
3. **변경 시 재검증:** 도면이 바뀌면 해당 근거에 의존한 결과를 무효화하고 영향을 받은 단계만 재실행한다.

## 3. 핵심 사용 흐름

예시 요청: “세척 장비에 쓰던 브래킷을 찾아줘. 장착 구멍 간격은 40mm이고 스테인리스야.” 사용자가 사진 또는 스케치를 함께 넣을 수 있다.

1. 자연어에서 사용 목적, 필수 조건, 미확정 조건을 추출한다. 별칭을 도번과 연결하되 출처 없는 연결은 확정하지 않는다.
2. 도번 exact lookup, BM25, 의미 검색, 이미지·형상 검색에서 후보를 모은다.
3. 후보가 비슷하면 Agent가 판단을 뒤집을 수 있는 조건을 골라 `read_region`, `query_dimensions`, `compare_revisions` 중 필요한 도구를 호출한다.
4. 형상은 비슷하지만 42mm인 후보는 탈락시킨다. 40mm 후보라도 재질 근거가 없으면 보류한다.
5. 자료로 확인할 수 없는 조건은 사용자에게 짧은 질문 하나로 요청하거나 근거 부족으로 남긴다.
6. 결과마다 선택·탈락·보류 이유와 도면의 해당 영역을 표시한다.
7. 개정판을 추가하면 기존 결과를 “재검증 필요”로 바꾸고 영향받은 조건을 다시 검사한다.

치수·재질·개정 조건 일치는 설계 안전성이나 실제 조립 적합성 전체를 보장하지 않는다. UI에서는 “확인된 조건 일치”로 표시한다. 지원하지 않는 GD&T, 하중, 피로, 제조 공정 조건은 미확인 항목으로 남긴다.

## 5. 시스템 구조

Frontend: React·TypeScript. FastAPI가 검색·실행·결과·평가 API를 제공한다. Python worker가 LangGraph workflow를 수행하며 PostgreSQL에 업무 상태와 checkpoint를 저장한다. pgvector는 의미 검색, BM25 인덱스는 키워드 검색을 담당한다. 도번·개정·tenant 조건은 별도 구조 필터로 적용한다.

PDF·이미지 입력은 파서와 OCR/VLM 경로를 구분한다. STEP은 CAD kernel에서 실제 geometry를 읽어 파생 특징과 표시용 mesh를 생성한다. 3D 화면이 장식용 모델에 그치지 않도록 입력 STEP hash와 특징 hash를 결과에 연결한다. 최초 지원 형식은 PDF·PNG·JPEG·STEP으로 제한하고 DWG 지원은 표기하지 않는다.

실행 그래프: 요구 추출 → 검색 계획 → 후보 검색 → 조건 검증 → 반례 탐색 → 추가 근거 검색 또는 사용자 질문 → 최종 결과. 분기마다 호출 예산과 취소 상태를 확인한다. 별도 변경 이벤트가 이전 결과의 증거 의존성을 검사해 재검증 실행을 만든다.

Agent가 생성하는 것은 허용된 연산을 조합한 검색 도구 명세다. 예를 들어 의미 검색 뒤 특정 치수와 개정 상태를 필터링하는 typed plan을 만들 수 있다. 서버가 스키마·권한·호출 예산을 검증한 뒤 실행한다. 모델이 만든 임의 Python·shell 코드를 서버에서 실행하지 않는다.

실제 프레임워크·모델의 버전은 구현 시 설치 가능성과 API 접근 권한을 확인하고 lockfile과 실험 manifest에 고정한다. 현재 설계 문서의 기능 설명을 설치·실측 성공으로 해석하지 않는다.

### 저장 계약

| 엔터티 | 필수 정보 |
|---|---|
| DrawingRevision | tenant, document ID, revision ID, 파일 hash, source, ingestion time, supersedes, 승인·유효 상태 |
| ExtractedFact | field, value, unit, page, bounding box 또는 CAD feature reference, 추출 방식, source hash, 불확실성 |
| Requirement | 조건, 단위, required 여부, 사용자 원문 위치, 확인 상태 |
| Evidence | requirement, candidate revision, fact reference, 충족·불충족·미확인, 검증기 버전 |
| Run | tenant, run ID, 상태, dataset/index snapshot, prompt hash, provider/model, budget, checkpoint |
| ToolCall | tool, arguments hash, observation hash, attempt, 지연, 오류 분류, trace reference |
| Decision | candidate, evidence refs, 결과 상태, created snapshot, stale 여부 |
| Evaluation | split, 데이터·코드 hash, seed, baseline, 원시 예측, metric 집계, 실패 목록 |

최신 개정은 파일 이름의 문자열 정렬로 정하지 않는다. supersedes 관계와 승인·적용 범위로 결정하고, 관계가 모순되면 보류한다. 실행마다 읽는 snapshot을 고정하고 결과 확정 시 변경 여부를 다시 확인한다.

### 실패와 복구

- 외부 모델 timeout·429·5xx는 제한된 재시도 후 원인을 표시한다. 다른 모델로 바꾸면 provider 변경을 trace에 남긴다.
- 모델 출력 schema 오류는 제한된 수리 시도 후 실패 처리한다. fallback 결과를 원래 모델의 성공으로 집계하지 않는다.
- worker lease·heartbeat와 멱등 키를 통해 중복 업무 결과를 막는다. 외부 모델 호출 자체는 crash 시 중복될 수 있으므로 exactly-once 호출을 주장하지 않는다.
- tenant·run·tool·입력 hash·snapshot·버전을 포함한 캐시 키를 사용한다. 데이터 개정 시 캐시를 재사용하지 않는다.
- 체크포인트 이후 중단, 결과 저장 직전 중단, 중복 재개, 사용 중 도면 개정, 사용자 취소를 각각 검증한다.
- 도면 안의 지시문은 자료로 취급한다. 도구 권한을 늘리거나 비밀 값을 반환하는 명령으로 실행하지 않는다.

## 6. 면접관이 직접 쓰는 데모

첫 화면 설명: **“닮은 도면 중에서 조건에 맞는 부품을 찾아보세요.”**

첫 화면에는 질문, 참고 이미지, 필수 조건을 배치한다. 가운데에는 후보 도면을, 오른쪽에는 선택·탈락·미확인 근거를 표시한다. 세부 trace·비용·평가 정보는 펼쳐서 볼 수 있도록 하고 일반 사용 흐름을 가리지 않는다.

| 시나리오 | 사용자 조작 | 실제로 확인되는 변화 |
|---|---|---|
| 비슷한 부품의 다른 규격 | 필요한 구멍 간격을 40→42mm로 변경 | 같은 후보 집합에서 조건 근거에 따라 선택·탈락이 바뀜 |
| 부족한 정보 | 재질 표시가 빠진 도면으로 변경 | 추측 대신 추가 검색·질문 또는 보류 |
| 개정판 도착 | 준비된 Rev.C를 프로젝트에 추가 | 과거 결과가 stale이 되고 영향을 받은 근거 재검증 |
| 중간 중단 | 관리자용 장애 체험 실행 | worker 종료를 backend에서 실제 유발하고 저장 상태로 재개 |
| 방식 비교 | 고정 workflow·단일 Agent·반례 Agent 선택 | 동일 입력의 결과·호출 수·지연·비용 비교 |

각 방문자는 분리된 데모 workspace를 사용한다. 장애 체험은 해당 workspace의 실행에만 작용한다. 모든 방문자에게 공유되는 process를 종료하지 않는다.

Live 실행과 기록 재생을 화면에 명확하게 구분한다. 재생은 저장된 실제 실행의 입력 hash·모델·시간과 함께 표시한다. 모델 API가 연결되지 않은 규칙 기반 체험을 LLM 실시간 실행으로 표시하지 않는다.

데모의 그래프는 기록된 tool event에서 생성한다. 미리 정한 정답을 입력에 상관없이 반환하거나 성공률을 하드코딩하지 않는다. 화면 녹화·스크린샷은 검증한 배포 버전에서 생성한다.

## 7. 데이터와 연구 설계

### 데이터 두 축

**통제 데이터:** 직접 제작하는 브래킷·플랜지·축·하우징 등 30개 독립 설계 family와 각 family의 개정·치수·재질 변형으로 최소 180개 도면을 목표로 한다. 원본 STEP, 2D 도면, 사람이 읽을 수 있는 조건 표와 정답을 함께 관리한다. 추출기 입력에는 정답 sidecar를 전달하지 않는다. 수정 가능한 패러미터는 평가자가 읽는 gold 데이터와 별도 경로로 보관한다.

**외부 데이터:** Fusion 360 Gallery의 geometry 데이터를 독립적인 검색·형상 실험 후보로 조사한다. 개정판·재질·공차 정답이 제공된다고 가정하지 않는다. 다운로드·배포 조건을 확인한 뒤 원본을 재배포하지 않는 가져오기 경로를 우선 사용한다. 실제 독립 데이터에 대한 추출·검색 결과가 없으면 일반화 성능을 주장하지 않는다.

외부 CAD에 직접 부착한 업무 조건은 “외부 형상 + 합성 조건”으로 표기한다. 실제 제조 현장의 요구 사항이나 전문가 승인 정답으로 소개하지 않는다.

### 분할과 누수 방지

- 최소 240개 통제 질의를 목표로 하되 design family 단위로 개발·검증·test를 분리한다. 동일 형상 및 그 개정판이 split을 넘지 않게 한다.
- 쉬운 도번 질의, 한국어 별칭, 이미지 질의, 한 조건만 다른 hard negative, 정답 없음, 근거 부족, 단위 혼동, 개정 충돌을 포함한다.
- test는 baseline과 budget을 정한 뒤 동결한다. threshold·prompt 선택은 검증 split에서 수행한다.
- 이미지 perceptual hash·geometry hash·파일 hash로 중복을 점검한다. 질의 표현 변형을 독립 표본으로 과대 집계하지 않는다.
- 골드 작성 경로와 검증기 구현을 분리하고 외부 표본은 원본과 수동 대조한 항목만 평가한다. 외부 전문가 검토가 없으면 그 한계를 표시한다.

### 비교 방법

| 방법 | 비교 이유 |
|---|---|
| 도번·BM25 검색 | 키워드 기준선 |
| Hybrid + reranker | Agent 없이 검색 품질을 높인 기준선 |
| Hybrid + 결정적 조건 검증 | LLM 추가 탐색 없이 규격 필터만으로 해결되는 범위 측정 |
| 고정 multi-step workflow | 동적 tool 선택의 필요성 측정 |
| 단일 ReAct Agent | 역할 분리의 효과 측정 |
| FitWitness 전체 | 반례 탐색·역할 분리·선택적 추가 검색 조합 |

Agent 없는 비교군에도 동일하게 접근 가능한 원본 자료와 도구 결과를 제공한다. 동일 provider/model로 방법 효과를 먼저 비교하고, 모델 간 비교는 별도로 한다. 평가용 call/token budget은 검증 단계에서 고정하고 동일 budget 비교와 무제한 품질 참고치를 구분한다.

### 지표

- Retrieval: Recall@5, nDCG@10, 도번 exact 정확도. revision-aware relevance로 집계한다.
- 추출: field 단위 정확도, 단위 변환 오류, 출처 영역 정확도.
- 판단: 필수 조건 충족 후보 선택 정확도, 잘못된 조건 일치 판정 비율, 보류율, coverage-risk 곡선.
- 근거: 인용 영역 유효성, 근거로 지지되지 않는 주장 비율, 탈락 근거 정확도.
- 운영: 성공 run 비율, tool call 수, 실제 token·비용, warm/cold p50·p95 지연, 복구 시간, stale 결과 차단률.
- 변경 후 재검증: 전체 재실행 대비 도구 호출·비용 절감과 최종 결과 일치.

모델 실험은 고정된 평가 표본에 최소 3회 반복한다. family 단위 bootstrap 신뢰구간을 보고하며 질의 표현 변형의 상관을 반영한다. 검증기·이벤트·권한 불변식 테스트는 결정적으로 실행한다. 승률만 골라 표시하지 않고 baseline이 더 좋은 경우와 실패 예시도 함께 남긴다.

주요 연구 질문은 “같은 예산에서 동적 반례 탐색이 고정 workflow보다 잘못된 조건 일치 판정을 줄이는가?”다. 차이가 입증되지 않으면 연구 결과로 그대로 보고하고 우월하다는 소개 문구를 쓰지 않는다. 기능 완성과 성능 우위 입증을 별도 상태로 관리한다.

## 8. 검증·완료 기준

1. 새 저장소의 clean checkout에서 설치·마이그레이션·샘플 적재·실행이 문서대로 된다. 로컬 편의 모드와 실제 PostgreSQL 통합 검증을 구분한다.
2. 두 provider로 실제 tool-calling workflow와 실패 경로가 실행된다. 키 부재로 skip된 테스트는 통과로 집계하지 않는다.
3. 모달리티별 검색이 실제 인덱스에서 실행되고, 필수 조건 결과는 원본 근거로 검증된다.
4. checkpoint 복구는 실제 worker 중단·재시작으로 확인한다. 결과 중복·tenant 간 공유·stale 결과 확정을 막는다.
5. 대표 데모 5개를 desktop·mobile에서 검증한다. 오류·빈 결과·보류·취소·중복 클릭을 포함한다.
6. CI에서 unit·API·DB integration·browser E2E·고정 회귀를 실행한다. 실측 LLM 실험은 비용을 통제하는 별도 수동 workflow로 둔다.
7. 최종 코드에서 전체 검증을 두 번 반복한다. 각 반복은 새 테스트 DB와 새 브라우저 세션을 사용한다. 수정하면 영향을 받은 검증과 최종 gate를 다시 실행한다.
8. 배포 URL, health의 commit SHA, 평가 manifest의 SHA, README의 결과가 일치한다. 데모 영상·캡처는 해당 배포 버전에서 수집한다.
9. README에서 구현·실측·기록 재생·계획 상태를 구분한다. 성능 수치는 원시 결과로 추적 가능해야 한다.
10. 비용·성능 우월성이 입증되지 않거나 필수 provider 실측·배포 검증이 막혀 있으면 해당 항목을 미완료로 명시한다.

성공률·지연 목표를 달성 결과처럼 미리 쓰지 않는다. 예를 들어 불변식 테스트에서 잘못된 확정이 0건이어도 실제 산업 데이터에서 오류가 없다는 뜻은 아니다.

## 9. 구현 순서와 산출물

아래는 의존 관계를 보여주는 단계이며 상세 구현 계획·작업량 추정은 설계 검토 후 작성한다.

4. checkpoint·멱등성·변경 무효화·tenant 격리·관측을 검증한다.
5. 사용자 데모와 평가 비교 화면을 연결한다.
6. 고정 실험, Docker·CI·브라우저 검증, 배포, 영상, 한글 README와 제출용 PDF를 정리한다.

예정 저장소 이름은 `fitwitness`이며 아직 사용 가능 여부나 생성 완료를 뜻하지 않는다. 사용자의 기존 저장소는 수정하지 않는다. 공개/비공개가 명시되지 않았으므로 검증 중에는 비공개를 기본으로 제안한다.

## 11. 설계 자체 점검

- 검색·개정 비교의 선행 제품 존재를 명시했으며 독창성의 범위를 과장하지 않았다.
