## 자격요건·우대사항

- LangChain/LangGraph와 Claude는 실제 앱·API·도구 사용 기록이 있습니다. 최종 provider gate `37321337436`에서 현재 코드로 Claude 세 구조 3/3 완료, 실제 model/tool usage와 비용까지 보존했습니다. OpenAI는 선택적 어댑터만 유지하며 최종 측정 범위에서 제외했습니다.
- VLM은 operator opt-in이며 관측은 항상 `uncertain`입니다. 이번 실측23/36은 추출·누락 판정이며 업무 적합성 정확도가 아닙니다.
- PostgreSQL checkpoint·lease·worker 종료 복구와 제한된 API 재시도를 구현했습니다. 수일간 작업·human resume·외부 청구 exactly-once는 미검증입니다.
- Codex 개발·리뷰·회귀 수정 기록이 있습니다. 사용하지 않은 Claude Code나 측정하지 않은 생산성 향상률을 주장하지 않습니다.
- 한국어 재현 문서와 원시 결과를 제공합니다. private 저장소이므로 공개 오픈소스 기여로 소개하지 않습니다.
- 학위·실무 기간은 프로젝트만으로 증명할 수 없으며 지원자의 실제 이력과 별도입니다.

| 칸 구조 읽기(`claims/official.py`) | 빈 서식에서 읽은 값 0개. 합성 120건의 값을 서식에 채워(위치 0~6pt 흔들림, 옆 칸에 읽으면 안 되는 값 포함) 1200필드를 5단계로 읽어 실제 서식·다시 그린 판 모두 전부 정답 |
| 파이프라인 (다시 그린 판, 120건) | 필드 98.6%, 잘못 지급 0, 잘못 부지급 0, 자동 처리 88.5%(텍스트 층과 같음). 같은 서류를 칸 구조 읽기 없이 읽으면 필드 64.9%, 진단일·합계 0% |
| 게이트 | `claims_official` 스위트와 대조군(칸 구조 읽기 없는 실행과의 격차 ≥ 0.05) |

**측정하면서 고친 것.** 라벨에 붙여 쓴 값이 라벨과 한 단어가 되어 사라진 것, 서식 줄에서 3pt 이상 벗어난 값이 다른 줄로 갈려 년·월·일 순서가 뒤바뀐 날짜(틀린 날짜가 나옴), 서식이 찍어 둔 공백 위의 값이 한 글자씩 갈린 것. 그리고 정책의 틈 하나: 신뢰도가 바닥 아래인 건이 깨끗이 읽은 진단코드 하나만으로 부지급이 되던 것을 담당자 확인으로 보냅니다(R-DOUBT-01).

**한계.** 값을 넣은 위치와 방식은 제가 서식에서 잰 것이라 병원 소프트웨어의 실제 출력과 다를 수 있고, 이 결과는 "서식의 칸 구조를 따라 값을 찾는 것"의 증거이지 실제 병원 서류 성능이 아닙니다. 두 서식만이고 입퇴원확인서·수술확인서·청구서·진료확인서와 간이 계산서(별지 제12호)는 읽지 않습니다. 스캔한 공식 서식은 칸 구조로 읽히지 않습니다. 서식 PDF는 저장소에 넣지 않았습니다.

### 프롬프트 비교 결과

같은 판정 과제(합성 PDF에서 뽑은 사실로 match, mismatch, unknown을 고르는 것)에서 프롬프트 네 가지를 비교했습니다. 기준(발행된 파일럿의 프롬프트), 절차를 적어 준 것, 요구 조건마다 짧은 근거를 쓰게 한 것, 예시 네 개를 넣은 것입니다. dev 6개 family 36건에서 고르고 test 4개 family 24건에서는 승자와 기준만 한 번 쟀습니다. 규칙은 코드가 강제합니다([prompt_experiment.py](../src/fitwitness/evaluation/prompt_experiment.py)).

**Claude Haiku 4.5, 반복 1회** (GitHub Actions 실행 37809745922, 상한 0.8달러, 실측 총비용 0.34달러. 기록: `docs/evaluation/prompts-claude.json`)

| 프롬프트 | dev 정확도 | 잘못된 일치 | 입력 토큰 | 출력 토큰 | dev 비용 |
|---|---|---|---|---|---|
| 기준 | 36/36 | 0 | 44,839 | 2,058 | $0.055 |
| 절차 명시 | 36/36 | 0 | 48,907 | 2,058 | $0.059 |
| 근거를 쓰게 함 | 36/36 | 0 | 51,175 | 4,695 | $0.075 |
| 예시 넣기 | 36/36 | 0 | 107,479 | 2,058 | $0.118 |

네 프롬프트 모두 36건을 전부 맞혔고, 같은 방식으로 정한 승자는 기준(동률이면 출력 토큰이 적은 쪽, 그다음 이름 순)이었습니다. test 24건에서 기준도 24/24였습니다. **이 과제는 이 모델에게는 천장입니다.** 프롬프트를 바꿔도 정확도 차이가 없고 비용만 달라집니다(근거를 쓰게 하면 1.35배, 예시를 넣으면 2.14배). 그래서 이 결과는 "더 정교한 프롬프트가 더 낫다"를 지지하지 않고, 이 과제에서는 가장 짧은 프롬프트로 충분하다는 것만 말합니다. 반복이 1회이고 family가 6개라 아주 작은 차이는 볼 수 없습니다.

**Qwen3-1.7B, CPU, float32, 반복 1회** (GitHub Actions 실행 37844924884, 유료 호출 없음. 기록: `docs/evaluation/prompts-local.json`). 이 모델은 발행된 파일럿에서 75%였으므로 프롬프트가 영향을 줄 여지가 있었습니다.

| 프롬프트 | dev 정확도 | 완료한 호출 | 잘못된 일치 | 출력 토큰 | 중앙 지연 |
|---|---|---|---|---|---|
| 기준 | 27/36 (75.0%) | 36/36 | 8 | 846 | 24초 |
| 절차 명시 | 21/36 (58.3%) | 36/36 | 15 | 802 | 26초 |
| 근거를 쓰게 함 | 10/36 (27.8%) | 19/36 | 8 | 3,527 | 55초 |
| 예시 넣기 | 21/36 (58.3%) | 36/36 | 9 | 714 | 72초 |

기준 프롬프트가 승자였고, test 24건에서 기준은 17/24(70.8%)였습니다. dev의 75.0%와 비슷합니다. 기준과 짝지어 뺀 차이는 절차 명시 −16.7%p, 예시 넣기 −16.7%p, 근거를 쓰게 함 −47.2%p이고, family 단위 부트스트랩 95% 구간은 세 가지 모두 0을 포함하지 않습니다.

**읽는 방법.** 이 작은 모델에서는 지시를 더한 프롬프트가 더 낫지 않았고 오히려 나빴습니다. Claude에서는 모두 천장이라 차이가 없었으므로, 두 모델을 합쳐 말할 수 있는 것은 "더 정교한 프롬프트가 더 낫다는 근거는 얻지 못했고, 기준 프롬프트가 둘 다에서 가장 좋거나 같았다"까지입니다. 숫자가 말하지 않는 것도 있습니다.

- 표본이 작습니다. 6개 family에 반복 1회이고 온도 0.7이라, 구간이 0을 피했다고 해도 실행을 다시 하면 값이 달라질 수 있습니다. 모델도 하나입니다.
- 근거를 쓰게 한 방식은 36건 중 17건이 답을 내지 못하고 오류로 끝났고 이는 틀린 것으로 셉니다. 오류의 종류는 로그에 찍히지 않았고 원본 출력은 실행의 산출물에만 있는데 이 환경에서는 그 파일을 내려받을 수 없어 확인하지 못했습니다. 출력 상한이 400토큰이라 잘렸을 가능성이 있으나 확인한 것이 아닙니다. 끝낸 19건만 보면 10건을 맞혔습니다.
- 어느 프롬프트도 고치지 못한 약점이 있습니다. 근거 사실이 빠진 사례는 dev 6건 모두에서 네 프롬프트 전부가 `match`로 답했고(범주 정확도 0), test의 4건도 그랬습니다. 이 모델에게 "없으면 모른다고 하라"는 지시는 프롬프트 수준에서는 먹히지 않았습니다.
- 범주별로 보면 한 범주에서 기준보다 나아진 프롬프트는 다른 범주에서 크게 나빠졌습니다. 절차 명시는 단위에서 1.0 대 0.83으로 올랐지만 치수에서 0.33 대 0.83으로 내려갔고, 예시 넣기는 치수에서 1.0 대 0.83으로 올랐지만 단위에서 0.0 대 0.83으로 내려갔습니다. 범주마다 6건이라 이것도 우연일 수 있습니다.

**과정의 기록.** 처음에는 bfloat16, 반복 2회로 돌렸고 CPU에서 느려 워크플로의 시간 제한(5시간 39분)에 걸려 취소되었습니다. 보고서가 없으므로 그 실행의 숫자는 어디에도 쓰지 않았습니다. float32로 바꾸고 반복을 1회로 줄여 다시 돌린 것이 위의 결과입니다. 프로토콜은 그대로 지켰습니다. 결과를 본 뒤 프롬프트를 고치지 않았고 test는 한 번만 쟀습니다.
